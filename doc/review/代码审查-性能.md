# cat 项目代码审查 — 性能维度

> 子 agent：性能专家
> 项目类型：自研 C++ Vulkan/GLES 渲染引擎（非 UE）
> 审查范围：cat / catbase / catui / catvulkan / catwindows

## 批次 1：渲染热路径核心（scene / world / object / mesh / primitive）

### Critical
- [性能] `cat/object.cpp:149-155` — `Object::globalMatrix()` 每次调用沿父链递归到根（无缓存）。设场景层级 N、平均深度 D，则 `Scene::draw` → `Object::draw` 递归一次会让每个节点重新求一次全链矩阵，总复杂度 **O(N·D)**。
  - 调用链：`Object::draw` → `globalMatrix()`（每帧每个 Object 至少 1 次，若有 skin 则 2 次）← `Mesh::draw` ← `Scene::draw` ← `World::draw`（每帧）
  - 修复建议：在 `Object::draw` 入参里传入 `parentGlobal`，子节点用 `parentGlobal * localMatrix()` 直接得到自己的 global；或在 `Transform` 上加 dirty flag 缓存 global matrix（dirty 通过 setMove/setRotate/setScale 时上抛给所有子节点）。
- [性能] `cat/object.cpp:114-141` — `Object::draw` 中每次都 `scl::matrix mat = globalMatrix()` 然后 `selfMvp = mat; selfMvp.mul(mvp);`，有 skin 时再算一次 `globalMatrix` 并做 `matrix::inverse`。结合上一条，递归路径里 inverse 也跟着递归翻番。
  - 修复建议：globalMatrix 求一次缓存到局部；只有 skin enable 时才求 inverse；inverse 也可缓存（仅 transform 改变时失效）。
- [性能] `cat/primitive.cpp:647-657 / 623-644 / 488-564` — `Primitive::boundingBox()` 会触发 **GPU 顶点缓冲回读**（`m_render->readVertexBuffer`），每次还 `new scl::varray<vector3>` + `result.resize(m_vertexCount)`；若该函数在 culling/拾取/编辑器选中显示等热路径被调用 = 灾难级 stall（vulkan readback 需要等帧完成）。
  - 调用链：`Primitive::boundingBox()` ← `Mesh::boundingBox()` ← `Object::boundingBox() const`。
  - 修复建议：mesh 加载完成后立刻在 CPU 端算一次 `Box` 并缓存到 `Primitive`/`Mesh`，运行时直接返回；CPU 端保留 position buffer 副本或在 `_loadVertex` 时顺便累加 min/max。
- [性能] `cat/primitive.cpp:191-224` — `Primitive::draw` 中 `m_shader->shader(m_render)` 每帧每 primitive 调用，需确认 `Shader::shader(IRender*)` 是 O(1) 命中（看 shader.cpp）；若内部走 hash 查询则每帧 N 次。同时 `isPick ? registerPickPrimitive(this)` 在 pick 模式下每帧也是 N 次。
  - 修复建议：non-pick 路径不要走 `registerPickPrimitive`；shader handle 在 `setShader` 时就拿一次缓存到 Primitive 成员。
- [性能] `cat/scene.cpp:95-99 / 97-141` — `Scene::draw` 平铺迭代所有顶层 object，**无视锥剔除（frustum culling）**、无任何分桶/排序。1080p/60fps 场景下，移动端必须有 culling，否则空跑大量 `Object::draw`/`Mesh::draw`。
  - 修复建议：在 `Object::draw` 顶部用 cached bounding box vs frustum 平面做剔除；至少对 leaf mesh 做检查。
- [性能] `cat/object.cpp:330-342 / 345-363`，`cat/scene.cpp:101-133` — `child(const char*)` / `findObject` / `childByID(recursive)` 是 **O(N) 字符串比较递归**，未缓存。若 UI/逻辑层每帧用 name 找子物体（很常见），就是每帧 O(N·D)。
  - 修复建议：`Env` 或 `Scene` 维护 `hash_table<String, Object*>` 与 `hash_table<int, Object*>`；name 改变/层级变化时同步。

### Warning
- [性能] `cat/object.cpp:215-223` — `Object::_objectIDMap()` 每次调用都判空，且全局是 `new` 出来的；建议改为函数内 `static` 局部 + `init` 一次。
- [性能] `cat/object.cpp:303-308` — `Object::_transform()` 懒分配 `new Transform`，每次 `position()/scale()/rotate()/matrix()/globalMatrix()` 都先判空。Object 几乎必然需要 Transform，建议直接以值类型内联在 Object 内（去掉一次 cache miss + 间接指针）。
- [性能] `cat/object.cpp:42` — Object 构造里 `_objectIDMap().add(this)`，第一次构造时还会触发 `new ObjectIDMap`+`init(MAX_OBJECT_COUNT)` 大块分配；建议在 Env/World init 时显式初始化，避免首个 Object 构造的隐藏延迟。
- [性能] `cat/scene.cpp:24-26 / object.cpp:52-54` — `Scene::~Scene` / `Object::~Object` 串行 `delete m_childs[i]`，深层级 + 复杂场景下析构卡顿；建议在 release 时改为后序迭代展开（避免栈深递归）。
- [性能] `cat/world.cpp:7-12` — `World` 构造直接分配 `m_componentArrayTable.init(32 * 1024)`，无论是否使用 ECS。若 ECS 在本项目里基本空跑（看代码 `Scene::draw` 没走 ECS），是常驻浪费。
  - 修复建议：lazy init 或缩小初始容量。
- [性能] `cat/primitive.cpp:71-139` — `_loadVertex` 用栈数组 `int attrOffsets[1024]`（4KB）+ `new byte[bufferSize]` + 临时 buffer 大小没上限保护；加载期非热路径，但栈数组 1024 可能过大。
- [性能] `cat/primitive.cpp:386-408` — `setAttrs` 在 `attrCount > m_attrCount` 时 `delete + new`，但 `m_attrBufferIndices` 没有判断 NULL 就 memset；潜在 UB（虽不在每帧路径）。
- [性能] `cat/mesh.cpp:49-59` — `Mesh::draw` 没做任何 primitive 级别的剔除/批合并，每个 primitive 一个 drawcall；移动端建议 instancing/批合并；至少把 primitive 排序按 shader/pipeline 分组以减少状态切换。
- [性能] `cat/primitive.cpp:442-457` — `setVertices` 使用 `scl::tree<int, void*>` 临时容器（每次构造），加载期非热点，但 `scl::hash_table` / 固定数组（`attrCount<=16`）即可。

### Suggestion
- [风格] `cat/scene.cpp:12` — `#include <queue>` 但只在 `save()` 用到；可改用 `scl::ring_queue` 保持自研 STL 一致性。
- [API] `cat/object.h:77` — `const Object* skinRoot() const { return skinRoot(); }` 看上去是错的：const 重载里 `skinRoot()` 又会调到非 const 版本？需要确认是否会构成无限递归 / 不同分支选择问题。
- [性能] `cat/mesh.cpp:41` — `m_env->shaderCache()->getShader("object.vert", "object.frag", primitiveNode, skinJointCount)` 路径字符串作为 key 反复构造；建议 path 用编译期常量字符串或常量 id。
- [可读] `cat/object.cpp:91-100` — `node->has_matrix` 路径里手写 16 个分量赋值，可考虑用 `setByMatrix(scl::matrix(node->matrix))`。

## 批次 2：material / shader / shaderCache / shaderMacro / skin / animation / keyFrame

### Critical
- [性能] `cat/skin.cpp:73-86` — `Skin::generateJointMatrix` 每帧对每个 joint 调用 `m_joints[i]->globalMatrix()`，而 globalMatrix 又递归到根 → **O(joints × depth)** 矩阵乘；50 joint × 平均深度 5 = 至少 250 次 mat4×mat4。每个有 skin 的 mesh 每帧一次。
  - 调用链：`Skin::generateJointMatrix` ← `Object::draw`（每帧有 skin 物体）
  - 修复建议：在帧开始时用一次后序遍历预算所有 Object 的 globalMatrix（dirty flag + 缓存）；joint matrix 直接读缓存即可，避免重复递归。同时配合 SIMD（mat4×mat4 4 路 SSE）。
- [性能] `cat/animationChannel.cpp:189-205` — `AnimationChannel::apply()` 每帧每个 channel 调一次 `Object::objectByID(m_target)` 走 `ObjectIDMap` 查表；建议在 `load()` 阶段缓存 `Object*` 指针，避免每帧表查。一个角色几十条 channel × 多个角色 = 每帧几百次哈希查询。
  - 调用链：`AnimationChannel::apply` ← `Animation::update`（每帧 N 次）
- [性能] `cat/animationChannel.cpp:108-155` — `update()` 内构造一个临时 `KeyFrame temp(time)`（包含 union 初始化）只为做 `binary_search2`，建议改用 `binary_search` 仅以 `time` 作为 key，避免每帧分配/构造 `KeyFrame` × channel 数。

### Warning
- [性能] `cat/shader.cpp:25-48` — `Shader::shader(IRender*)` 在 `m_dirty == false && m_deviceShader != NULL` 时只是返回 `m_deviceShader`，OK。但 `Primitive::draw` 每帧每 primitive 进函数本体已是 inline 友好级别；可考虑直接缓存 `void* m_deviceShaderCached` 在 `Primitive` 上，避免每帧间接调用。
- [性能] `cat/shaderCache.cpp:23-66` — `getShader()` 每次都构造 `String key` 通过反复 `+=` 拼接（vsname + psname + 所有 macro name:value）；如果运行时切 macro，每次切换都是若干次堆分配 + memcpy。
  - 修复建议：1) key 使用 `xxhash` 直接哈希原始数据，存 `uint64`；2) 内部 `m_shaders` 改 `scl::hash_table<uint64, Shader*>`，O(1) 查询；3) `scl::tree<String, Shader*>` 是有序树，查找比哈希慢。
- [性能] `cat/shaderCache.cpp:27-49` — 对每个 macro 还做 `String name = macros[i].name; name.trim();` 在堆上复制再 trim；运行时切 macro 时无谓拷贝。
- [性能] `cat/shaderMacro.cpp:35-45` — `remove()` 用倒序 `erase_fast` 是 OK 的，但 `ShaderMacro m = m_macros[i];` 按值拷贝了 String，每个比较都一次拷贝；应 `ShaderMacro& m = ...`。`contains()` 同样问题（line 51）。
- [性能][BUG] `cat/shaderMacro.cpp:72-81` — `ShaderMacroArray::assign(const ShaderMacro* macros, const int macroCount)` 中 `clear()` 后循环 `add(m_macros[i])` —— 拼错了，应该是 `macros[i]`。清空后 `m_macros` 为空，循环用 `m_macros[i]` 越界（看起来 length==0 所以循环 0 次……不对，循环到 `macroCount`），是真 BUG。
- [性能] `cat/shader.cpp:51-86` — `_loadfile` 用 `new char[buflen]` + `delete[]`，shader 编译时机若是首次 draw 则会卡顿一帧；建议 1) shader cache 在 loading 阶段强制 warm-up（预编译所有变种）；2) 用 `scl::file` 直接读到固定/复用 buffer。
- [性能] `cat/skin.h:24` — `const Object* root() const { return root(); }` 形参一致 / 函数本身一致，会**无限递归**（编译期同 const-overload 选择规则下会调到自身）。极可能是 bug，会栈溢出崩溃，但因为没人调 const 版本所以没暴露。
- [性能] `cat/skin.cpp:88-133` — `Skin::root()` 用 `m_joints.contains(parent)` 线性查找一次循环，最坏 O(joints²)；不过只执行到 cache 命中之前，问题不大。
- [性能] `cat/animationChannel.cpp:76-100` — `load()` 每个 keyframe `new KeyFrame`，对长动画（几千 frame）应一次性 `varray<KeyFrame>` 数组化（避免 N 次 alloc + 指针间接 + cache miss）。`m_frames` 也建议改 `scl::varray<KeyFrame>`（值类型）。
- [性能] `cat/shader_gles.cpp:51-57` — `open_file` 用 `static const int FILE_LEN = 1MB; malloc(FILE_LEN); memset` —— 每个 shader 文件都分配 1MB 然后 memset，明显浪费；用 `fseek`/`ftell` 量身分配，或直接 `scl::file`（其他地方都用 `scl::file`）。
- [性能] `cat/shader_gles.cpp:140-154` — `load_shader_file` 用 `malloc/free`，与项目其余 `new/delete` 风格不一致，且没有 NULL 检查。

### Suggestion
- [API] `cat/material.h:24` — `release()` 是 public，被析构调用，没问题；但 `m_render` 在 release 里没用到，是不是漏了？资源生命周期靠 `m_textureFile` 引用计数？需要确认。
- [可读] `cat/shader.cpp:9-14` — `load` 仅更新文件名 + invalidate，未真正加载；接口名易误导，可考虑改 `setSource`。
- [性能] `cat/material.cpp:48-49` — `string256 fullPath = currentPath; fullPath += texture->image->uri;` 在 load 路径 OK，但 `string256` 是栈 256 字节，若路径深度超出会截断。
- [可读] `cat/animation.cpp:44` — `static_cast<uint>(m_time)`：`m_time` 是 `double`，毫秒模式下能撑 ~49 天循环；如果按秒则 ~4000 秒后回绕，需要确认单位。
- [性能] `cat/animationChannel.cpp:78` — `static_cast<uint>(times[i] * 1000)`：转毫秒可放 `Animation::load` 阶段一次性 SIMD 转。

## 批次 3：catbase（transform / camera / box / color / vertex / names / objectIDMap / string / yaml / def / IRender / IFileProvider / textureFile）

### Critical
- [性能] `catbase/cat/transform.cpp:15-41` — `Transform::matrix()` 的 dirty flag 本身很好，但与 `Object::globalMatrix()` 之间**没有联动**：父节点 Transform 没变也会被子节点重算（因为 globalMatrix 不缓存）。已在批次 1 标注 Critical；这里再次确认 `Transform` 端有 `m_changed`，但 `Object` 端没接住 → 整个 dirty 机制白做。
  - 修复建议：让 `Object` 持有 `m_globalDirty` + `m_globalMatrix`；`setMove/setRotate/setScale` 时除了 `Transform::invalidate()`，还要对自身和**所有子 Object** 递归设 dirty。
- [性能] `catbase/cat/IRender.h:96-112` — `draw2` 接口接 15 个参数（包含矩阵、joint matrix 指针、push const buffer、texture），每次每 primitive 都要按这个签名传一遍；在移动端 ARM 上参数主要走栈，**每 drawcall 几十字节栈写**；同时使得未来批合并/instancing 难以追加。
  - 修复建议：定义一个 `DrawCommand` 值类型，按 const-ref 传入；同时为后面合并/排序留口子。

### Warning
- [性能] `catbase/cat/transform.cpp:43-46` — `setByMatrix` 用 `scl::matrix::decompose` 拆 TRS 但**没有 invalidate**！结果调用 `setByMatrix` 后再 `matrix()` 直接返回旧的缓存值，**逻辑 BUG**。
- [性能] `catbase/cat/transform.cpp:15-41` — `Transform::matrix()` 每次 dirty 重算用 3 次 mat4×mat4（identity → scale → rotate → translate）。其实 TRS 矩阵有解析形式（直接填 12 个元素），可以省 2 次 64 FLOP 矩阵乘。
- [性能] `catbase/cat/camera.cpp:232-243` — `_front()` / `_right()` 每次都 `normalize()`（含 sqrt）；`orbit_right/orbit_up/move_front/move_side` 内多次重复调用（_front 内被算两次以上）。编辑器/相机交互密集时可见。建议缓存 `m_front, m_right` + dirty flag。
- [性能] `catbase/cat/box.cpp:54-83` — `encapsulate` 每次都先 `ensureMinMax()`（含 3 个 swap 判断），即使是顺序累加场景；建议构造时已保证有序，then `encapsulate` 跳过校验。
- [性能] `catbase/cat/box.h:17-18` — `isEmpty()` / `isValid()` 都调用 `.absolute()` 比 `infinity()`，每次构造临时 vector3 + 6 次浮点比较；高频使用（如 Mesh::boundingBox 累加）下浪费。建议用一个 `bool m_valid` 直接存。
- [性能] `catbase/cat/objectIDMap.h:73-79` — `init(MAX_OBJECT_COUNT=128K)` → 实际分配 `8 * 128K = 1M` 个槽位，大概 ~16~32MB 哈希表常驻；移动端内存吃紧。如果场景实际只有几千个 object，明显过预分配。建议根据典型场景规模分级。
- [性能] `catbase/cat/yaml.cpp:108-118` — `node::value()` 第一次调用时 `m_value.copy(data, len)` 分配并复制；如果短期反复获取同节点 value 没问题（cache 命中），但 `m_value` 在大量 yaml::node 临时对象上每个都自带一份；大文档解析时累积分配。建议直接返回 `c4::yml::csubstr` 引用 + 长度，让调用方决定是否拷贝。
- [性能] `catbase/cat/yaml.h:153-155` — `class node` 内含 `c4::yml::NodeRef + yaml::document + mutable scl::vstring`，文档拷贝（`yaml::document(c4::yml::Tree*)`）会拷贝整个 `c4::yml::Tree`，每个 node 临时对象都拷一份 Tree。`document::document(c4::yml::Tree* tree) : m_tree(*tree)` 是 deep copy，运行时 yaml 节点遍历时灾难性。**建议改为持引用/指针**。
- [性能] `catbase/cat/yaml.cpp:14-17` — `document(c4::yml::Tree*)` deep-copy 整个 tree 进入成员；如果 `node` 临时对象也走这个分支（line 67 用 `node.tree()`，line 72-75 用 `&doc->tree()`），每构造一个 node 就拷贝一棵树。需要确认 `node` 大量临时构造会不会触发；如果有可能是巨大开销。**强烈建议改为持有 `c4::yml::Tree*`**。
- [性能] `catbase/cat/def.h:91` — `MAX_OBJECT_COUNT = 128K` 太大，结合上面 ObjectIDMap 的 8 倍因子是 1M 槽位。
- [性能] `catbase/cat/vertex.h:136-209` — `vertex_color_uv` 等顶点结构非 `#pragma pack(1)`、未 `static_assert(sizeof == ...)`，编译器可能加 padding 导致 stride 与 `sizeof()` 不匹配；上传到 GPU 时分配带宽浪费且对齐错位风险。建议 `static_assert(sizeof(vertex_color_uv) == 24)` 等。
- [性能] `catbase/cat/IRender.h:38-163` — 所有 `createVertexBuffer/writeVertexBuffer/...` 都是 1 buffer 1 调用、无批量；加载大模型时可能产生几百次 backend 接口调用，每次都过 vtable + Vulkan API。建议加批量上传/批量创建接口（一次性 `writeVertexBuffers(srcs[], dsts[], sizes[], count)`）。

### Suggestion
- [性能] `catbase/cat/color.h:44-58` — `blendColor` 每分量 `*x/0xFF` 浮点替代品用整数除法，移动 CPU 除法慢；建议 `(x * a + 127) >> 8` 近似或查表。
- [可读] `catbase/cat/camera.cpp:23` — `m_zRange{negative_one_to_one}` 默认值是 GL；如果 backend 已经是 Vulkan，把默认改为 `zero_to_one` 可避免每次 setProjection 都手动设。
- [性能] `catbase/cat/box.cpp:8-13`，`combine` 与 `intersection`：`Box r = combine(*this, other); *this = r;` 多了一次 Box 值复制（48 字节）；可直接在自身上算。
- [API] `catbase/cat/textureFile.h:11-29` — `width/height/pitch/pixel` 在默认构造里未初始化（只构造了 name/texture/counter）；之后访问可能读到垃圾值。
- [API] `catbase/cat/objectIDMap.h:68` — `assert(m_id + 1 > 0)` 仅在 debug 生效；正式运行下 id 溢出回绕会与已存活 object 冲突；建议改成 `release`-friendly 检查或用 uint64。
- [API] `catbase/cat/string.h` — `using String = scl::vstring;` 这意味着 `cat::String` 是堆分配，作为 Object/KeyFrame/ShaderMacro 等的成员每个都自带堆指针；考虑高频小字符串场景下用 `scl::sstring256/64` 之类 SSO。

## 批次 4：cat 渲染其他对象（env / terrain / light / skybox / grid / gltfLoader / gltf_raw_render / component）

### Critical
- [性能][BUG] `cat/env.cpp:56-61` — `Env::getDefaultMaterial()` **每次调用都 `new Material()`**！`cat/primitive.cpp:187` 中每个使用 default material 的 primitive 都会触发一次 `new`，于是：1) 加载阶段每 primitive 多一次堆分配 + texture file 查表；2) primitive 析构时 `safe_delete(m_material)` 删的是自己那份，所以不会 double-free，但 default material 完全失去"共享"语义。
  - 修复建议：`Env` 持有一个 `m_defaultMaterial`，第一次访问时构造、后续返回同一指针；`Primitive::release()` 仅当 `m_material != env->getDefaultMaterial()` 才 delete。
- [性能][BUG] `cat/terrain.cpp:72` — `m_primitive->setIndices(m_indices, 3, ELEM_TYPE_UINT32);` 这里只传了 **3** 个索引（应是 `INDEX_COUNT = (4-1)*(4-1)*6 = 54`）；上一行注释了正确的版本。结果地形只会画 1 个三角形。注释里 `jm_primitive` 的拼写错误说明是临时调试遗留。
- [性能] `cat/gltf_raw_render.cpp:20-28 / 76-99` — `glcheck` 宏在**每个 GL 调用后**调 `glGetError()`，会**强制 GL 驱动同步**（在 tile-based GPU 上等价于一次 fragment flush）。在移动端 GLES 路径上是显著 GPU stall。
  - 修复建议：debug 模式才启用 `glcheck`，release 直接 `(x)`。

### 最该优先修的 3 件事

1. **`Object::globalMatrix()` + `Transform` dirty flag 联动失效（批次 1/3 Critical）**
   `Object::draw` 递归 + `globalMatrix` 沿父链递归，使得整帧矩阵复杂度 O(N·D)；同时 `Skin::generateJointMatrix` 每 joint 也调 `globalMatrix` 导致再叠一层 O(joints×depth)；`Transform::setByMatrix` 又忘了 invalidate。
   **修复**：在 `Object` 端加 `m_globalMatrix + m_globalDirty`，`set*` 时把 dirty 上抛到所有子节点；帧开始遍历一次写入 cache；`Object::draw` 把 `parentGlobal` 作为参数传递。

2. **Vulkan 渲染热路径栈/内存爆炸（批次 5 Critical）**
   - `init` 里 uniform buffer 48MB 常驻 host-visible（公式 `MAX_OBJECT × MAX_MATRIX × align`）
   - `draw2` 默认走 secondary command buffer per primitive
   - `DescriptorDataKey` 8KB 栈对象每 draw 构造、`PipelineKey` 用 `attrs` 指针做 key 导致 pipeline cache 失效
   - `_fillUniformData` 3KB memset per draw
   - `releaseVertexBuffer/IndexBuffer` `delete void*` UB
   **修复**：1) 重算 uniform buffer 大小（实际 mvp + joints，单帧 1 MB 内）；2) 默认 bindCommandBuffer 模式让整帧 1 个 secondary；3) `DescriptorDataKey` 缩到 16 槽；4) `PipelineKey` 用 attrs 内容哈希；5) 修 release `void*` UB。

3. **每帧 GPU 回读 / 隐式 stall（批次 1/4 Critical）**
   - `Primitive::boundingBox()` 触发 `readVertexBuffer`（vulkan map+memcpy），如果用于 culling/选中显示就是每帧 GPU stall
   - `gltf_raw_render.cpp` 每条 GL 调用后 `glGetError()` 强制 driver 同步
   - `gltf_do_render` 每帧 `glGetUniformLocation` 字符串查找
   - `terrain.cpp` 只画 3 个顶点（debug 残留）
   **修复**：加载阶段 CPU 端算并缓存 boundingBox；`glcheck` 仅 debug 启用；uniform location 在 shader 创建时缓存；修复 terrain `setIndices(m_indices, INDEX_COUNT, ...)`。
