## 专家 1：领域知识 / 注释正确性（gltf skinning）

### 1.1 矩阵乘法顺序与实现不一致（**主要问题**）

注释写：

```
M_joint = inv(mesh.global) * joint.global * IBM
```

但 `cat/skin.cpp:88-93` 的实际实现是：

```88:93:cat/skin.cpp
		m_jointMatrices[i] = m_inverseBindMatrices[i];
		m_jointMatrices[i].mul(m_joints[i]->globalMatrix());
		m_jointMatrices[i].mul(inverseMeshGlobalTransform);
```

`scl::matrix::mul` 在 cat 里是 `A.mul(B)` ⇒ `A = A * B`（左侧累乘到右），最终得到的乘法书写顺序是：

```
M_joint = IBM * joint.global * inv(mesh.global)
```

— 与注释里的顺序**完全相反**。

- 若 scl 是**行向量约定**（`v_out = v * M`，cat 里 mvp 链 `selfMvp = mat; selfMvp.mul(mvp);` 的写法强烈暗示就是行向量），那么注释里写的 `inv(mesh.global) * joint.global * IBM` **是错的**，正确的应该贴近代码顺序 `IBM * joint.global * inv(mesh.global)`。
- 若是列向量约定，注释才正确，但那样 `Object::draw` 里 `selfMvp = mat; selfMvp.mul(mvp);` 就不通了。

**结论**：注释里这一行公式按 cat 的 scl 行向量惯例**反了**。这个注释是这次新增的 6 行里"含金量"最高、最容易让读者引用，错了就会反复误导后来读 `_loadIBM` 的人。

**建议**：

```
// 蒙皮最终矩阵（行向量约定，v' = v * M_joint）：
//   M_joint = IBM * joint.global * inv(mesh.global)
// 与 Skin::generateJointMatrix 中 mul 顺序逐字对应。
```

### 1.2 "再乘上骨头当前帧的 global 矩阵，就得到顶点在当前动画姿势下的位置"

这里漏了第三步 `inv(mesh.global)`：实际上之后还要回到 mesh local space，否则蒙皮结果与 `Object::draw` 里 `selfMvp = mesh.global * mvp` 会双重叠加 mesh.global。直觉说明不一定要面面俱到，但既然下一行直接给了三项公式，直觉解释与公式之间留这个 gap 会让人困惑"那 inv(mesh.global) 是哪冒出来的"。

**建议**：直觉段也补一句 "再用 inv(mesh.global) 把结果送回 mesh 局部空间，方便上层统一乘 mvp"。

### 1.3 其他术语描述 OK

- "把顶点从模型空间搬到该骨头绑定姿势下的局部空间"：基本准确（严格说是 *bind-pose 下* model space → joint local space）。
- "数量必须与 joints 数量一致，缺失/损坏时整个 skin 不可用"：与 `Skin::generateJointMatrix` 的 `count = min(jointCount, m_inverseBindMatrixCount)` + NULL-joint 早退行为吻合，准确。
- 引用 `skin.inverseBindMatrices accessor` 也对得上 gltf 规范。

## 专家 2：cat 注释风格（"非显而易见才注释"）

### 2.1 头文件 + cpp 双份注释 — 这里恰好**合理**，不算冗余

cat 风格反对的是**"代码自己说明的事情再啰嗦"**（如 `// increment i`），不是反对在 .h 给一行术语展开。`_loadIBM` 这个函数名缩写不展开，外部 reader 看 .h 时只看得到一个 `scl::matrix*` 返回值，根本不知道是不是"In-Band Message"还是别的什么。

- **头文件那一行**（只展开缩写，1 行）：✅ 必要，且控制在最小成本。
- **cpp 里 6 行**（铺开作用 + 公式 + 数据源 + 失效约束）：✅ 也合理，因为 `_loadIBM` 后面的 component_type / type / 长度校验逻辑要靠这段 domain context 才能解释"为什么这些校验失败就直接返回 NULL"。

**结论**：双份不算冗余，分工清晰（.h 给签名读者，.cpp 给实现 reader），这是 cat 风格里允许的"非显然意图"注释。

### 2.2 唯一的过度部分

cpp 里 "见 Skin::generateJointMatrix" 这句指针对了，**但同时给出公式又给出跳转**，建议二选一：

- 既然已经把公式写出来，"见 Skin::generateJointMatrix" 可保留作交叉引用；
- 但 1.1 已说明公式与实现顺序冲突 — 必须先修公式，再保留这句跳转才有意义，否则读者跳过去发现对不上，反而是"误导性注释"，比无注释更糟。

## 专家 3：头文件版式 / 纵向对齐

`gltfLoader.h:64-78` 的 helpers 块：

```64:78:cat/gltfLoader.h
	// helpers (从 ShaderCache / Primitive / AnimationChannel 内的 cgltf 私有函数搬入)
	Shader*		_selectShader		(cgltf_primitive* src, int skinJointCount);
	byte*		_flattenVertexAttrs	(cgltf_primitive* src,
									 VertexAttr* outAttrs,
									 int& outAttrCount,
									 int& outVertexCount,
									 int& outStride);

	// IBM = Inverse Bind Matrices，gltf skin 里每根骨头一份的"逆绑定矩阵"。
	scl::matrix*_loadIBM			(cgltf_accessor* accessor, int outputCount);
```

两处版式问题：

1. **`(` 列对齐被打破**：原本 `_selectShader` / `_flattenVertexAttrs` / `_loadIBM` 的 `(` 都对齐到同一列（diff 里能看到旧版 `_loadIBM` 用了 4 tab，新版只剩 3 tab）。注释加入后，**`_loadIBM` 的左括号往左缩了一个 tab 列**，与同组的 `_selectShader` / `_flattenVertexAttrs` 不再对齐。cat 头文件里方法表的纵向对齐是显式追求的风格（看 line 52-58 `_loadScene` / `_loadNode` / `_loadSkinRecursive` / ... 一列对齐就能感受到），这是肉眼可见的回退。
2. **同组之间插了一行空行 + 注释**：把 `_loadIBM` 从 `_flattenVertexAttrs` 同组中视觉分离了出来。如果想给它一行 .h 注释，更稳的做法是**不插空行**，让注释直接贴在函数上方，与组内其他成员的"无注释"行视觉差仅一行注释：

   ```cpp
   	byte*		_flattenVertexAttrs	(cgltf_primitive* src,
   									 VertexAttr* outAttrs,
   									 int& outAttrCount,
   									 int& outVertexCount,
   									 int& outStride);
   	// IBM = Inverse Bind Matrices，gltf skin 里每根骨头一份的"逆绑定矩阵"。
   	scl::matrix*_loadIBM			(cgltf_accessor* accessor, int outputCount);
   ```

   并把 `_loadIBM` 前的 tab 数补回 4 个，恢复 `(` 对齐。

**建议**：删掉新加的空行，把 `_loadIBM			` 改回 `_loadIBM				`（4 tab）。

## 专家 5：可维护性 / 真值耦合

注释把"实现细节"（mul 顺序公式）**直接抄进 gltfLoader.cpp** 这一点本身就是一个**耦合点**：

- `gltfLoader._loadIBM` 只是**加载**数据，并不消费这个公式；
- 真正消费公式的是 `skin.cpp::generateJointMatrix`。

把公式注释放在加载端，后续若改了 `generateJointMatrix` 的 mul 顺序（例如未来切到 column-major、或加 root-motion 偏移），改的人**只会改 skin.cpp 而忘记这里**，注释马上 stale —— 这次已经发生过一次（公式和实现对不上，见 1.1）。

**建议**（任选其一）：

1. **首选**：把公式那一行**搬到 `skin.cpp::generateJointMatrix` 头部**（紧贴 mul 三连），`gltfLoader.cpp` 只保留 "IBM 是什么 + 见 Skin::generateJointMatrix 的公式" 一行指引；
2. 或：保留双份，但 cpp 末尾再补一句 `// 任何变化以 Skin::generateJointMatrix 为准`，让 reader 不至于在公式 stale 时被误导。
