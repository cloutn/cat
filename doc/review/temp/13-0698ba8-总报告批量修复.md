## 二、重点项详评

### C1（Critical）addChild 不解除旧 parent，可造成双父链
HEAD `cat/object.h:49`:
```49:49:cat/object.h
	void addChild(Object* c) { if (NULL != c) { c->m_parent = this; m_childs.push_back(c); } }
```
- 改写补 `c->m_parent = this` 是对的，但**没有从 `c->m_parent` 旧值的 m_childs 中摘除**。一旦调用方写：
  ```
  oldParent->addChild(node);   // 第一次
  newParent->addChild(node);   // 重新 parent
  ```
  `node` 同时存在于 `oldParent->m_childs` 和 `newParent->m_childs`；后续 `delete oldParent` 会递归 delete `node`，`newParent` 留悬垂指针，**正好把这次 commit 想修的 ~Object 悬垂回归**。
- 这是这次"批量修复"中最大的语义漏洞，因为另一条修复（~Object 自摘）建立的不变量是"m_parent 唯一指向 m_childs 包含我的那个父亲"，而 addChild 自己破坏了这个不变量。
- 修法：
  ```
  void addChild(Object* c)
  {
      if (NULL == c) return;
      if (NULL != c->m_parent) c->m_parent->_removeChild(c);
      c->m_parent = this;
      m_childs.push_back(c);
  }
  ```
  且 `_removeChild` 应保留可见性（friend 或 public + 文档）。

### C2（Critical）`s_objectIDMapReleased` 一次性标志被反思 commit 拆掉
0698ba8 引入：
```
+	assert(!s_objectIDMapReleased);
...
+	safe_delete(s_objectIDMap);
+	s_objectIDMapReleased = true;
```
HEAD（249d1e3 后）：
```277:279:cat/object.cpp
void Object::releaseObjectIDMap()
{
	safe_delete(s_objectIDMap);
}
```
但 HEAD 的 `~Object` 末尾仍调：
```70:70:cat/object.cpp
	_objectIDMap().del(this);
```
而 `_objectIDMap()` 是 lazy:
```163:171:cat/object.cpp
ObjectIDMap<Object>& Object::_objectIDMap()
{
	if (NULL == s_objectIDMap)
	{
		s_objectIDMap = new ObjectIDMap<Object>;
		s_objectIDMap->init(MAX_OBJECT_COUNT);
	}
	return *s_objectIDMap;
}
```
**进程退出顺序**：用户调 `releaseObjectIDMap()` 后，任何静态/全局持有的 Object 在 destructor 阶段析构时，会**重新 new 一份 ObjectIDMap 只为了 del(this)，再永远不释放**——双重问题：
1. 内存泄漏（重新 new 出来的 map 没人 release）
2. 在已"回收"语义下又把对象加进 map（add inside del path），违反 release 的单向终点不变量
   修法：恢复 0698ba8 的 `s_objectIDMapReleased` 一次性标志，或在 ~Object 中也做 `if (NULL != s_objectIDMap) ... del(this)`。本 commit 把它加上是对的，反思 commit 减回去是过度。

### H1（High）`_removeChild` 用 erase_fast 破坏顺序
```319:332:cat/object.cpp
void Object::_removeChild(Object* c)
{
	...
	m_childs.erase_fast(i);
	return;
}
```
- O(1) 摘除是用 `swap with back + pop`，**会把最后一个 child 顶到 i 位置**。
- 影响：
  - YAML 序列化（`save` 注释里就有按 m_childs 顺序写 childs 的草稿）顺序会随删除抖动。
  - `testCat/mainGUI.cpp:323 _onGUIObject(object->child(i), ...)` 这种用 int 索引迭代的 UI 树会乱跳。
  - gltfLoader 加载顺序与 SceneTree UI 顺序解耦后，diff 工具难以工作。
- 修法：要么写一个保序的 `m_childs.erase(i)`；要么在 ~Object 自摘场景里其实不必关心顺序（反正自己要走），但 reparent 场景必须保序。建议 `_removeChild` 默认保序，仅在 ~Object 中走 fast 版本。
