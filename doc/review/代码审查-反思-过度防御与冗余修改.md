## 一、严重 — 与项目约定/架构相冲突

### #1 `catbase/cat/objectIDMap.h` 引入 `scl::mutex` + `scl::atomic_inc`（commit `04dde69`）

**改动**：

- `m_id` 改 `volatile int`，`alloc_id` 用 `scl::atomic_inc(&m_id)` 替代 `++m_id`
- 新增 `scl::mutex m_mapMutex`
- `add` / `del` / `get` 入口全部 `scl::mutex_lock lock(&m_mapMutex)`

**问题**：

1. **直接违反 AGENTS.md「项目背景 §7」**：

   > 当前主线为**单线程**：游戏循环、渲染提交、资源加载都跑在主线程，**cat 模块内不引入 mutex / atomic / thread**。如未来引入多线程，需要先在本节补完整的线程模型说明再动代码。

   `catbase` 是比 `cat` 更基础的层（`cat代码风格.mdc §33`：`catbase` 不依赖其他模块），引入 `scl::thread.h` 之后整条依赖链都被传染。

2. **性能反作用**：`AnimationChannel::apply()` 每帧每 channel 调用 `Object::objectByID(m_target)`（见性能维度报告 Critical #19）。一个中型场景几百 channel × 60fps = 数万次 mutex 加解锁。原 review 总报告把 `objectByID` 列在"必修性能项"上，本提交反而**让它更慢**。

3. **review 文档对该条本来的判定**：崩溃安全维度只把它写在 Warning 级（不是 Critical），并附备注"主线程 only 时 OK，文档化即可"。`2049f99` 提交在 `animation.cpp` 已经用注释**正确处理过同一条**（见 `update` 函数顶部"约定单线程调用"注释），却又用 `04dde69` 在底层强加了锁。两条修复路径互相矛盾。

4. **`atomic_inc` 之后还要判 `newId <= 0`** —— 用原子操作绕开 UB 之后又要软判溢出，比 `02e49ab` 引入的 `m_id >= INT_MAX - 1` 检查更绕。

**建议**：

- 回滚 `04dde69`，保留 `02e49ab` 中 `alloc_id` 的 `m_id >= INT_MAX - 1` 检查（这一条是 release-safe 真问题）。
- 在 `objectIDMap.h` 顶部加一行注释：`// 单线程调用约定，详见 AGENTS.md §7`。
- 如果将来要加多线程，按 AGENTS.md 要求先补线程模型文档，再决定是加锁还是改 lock-free 容器。

### #2 `cat/skin.cpp::generateJointMatrix` NULL joint 静默兜底（commit `3df3ecb`）

**改动**（精简后）：

```cpp
for (int i = 0; i < count; ++i)
{
    Object* joint = m_joints[i];
    m_jointMatrices[i] = m_inverseBindMatrices[i];
    if (NULL != joint)
        m_jointMatrices[i].mul(joint->globalMatrix());
    m_jointMatrices[i].mul(inverseMeshGlobalTransform);
}
```

**问题**：

- NULL joint 用 `IBM * inverseMesh` 兜底，commit 注释自述"等价 bindpose"，但**任何一个关键 joint 缺失，整副骨架就会以"半 bindpose 半动画"的姿态渲染**，肉眼会看到关节穿模/扭曲；这种"看上去能跑、画出来是错的"是 review 总报告 §4 反复批评的反模式。
- 上游 `_loadSkin` 在 `_objectByNode` 失败时已经 `continue` 不 push 进 m_joints，正常路径下 `m_joints[i]` 不会是 NULL。这层兜底针对的是异常路径，本来就该 fail-loud。

**建议**：

- 早退条件改为：扫一遍 `m_joints`，**任一 NULL 则整体返回 NULL + log_error("skin invalidated")**，调用方退化到不蒙皮渲染。
- 这与 `3df3ecb` 自己对 `m_inverseBindMatrices == NULL` 的处理风格一致（早退 NULL），不应在同一函数里走两套策略。

### #14 `catbase/cat/yaml.cpp::node` 修「悬垂」反打碎引用语义（2026-05-31 P0-27 修复路径，已回滚）

**改动**（已回滚）：

按崩溃安全 review pass 3 的 P0-27 条目，把 `yaml::node` 的两个 ctor 改成「m_node 指向自身 m_document 内拷贝的 Tree」，意图消除「yaml::node 跨 document 生命周期工厂返回」的悬垂假设。第一版只改 ctor 立即崩在 `Scene::save → yaml::node::add`，第二版补 rule-of-five 后崩在 `set_value → _set_val`（seed 信息丢失），最终全部回滚。

**问题**：

1. **误读 ryml 与 cat 封装的引用语义**。`yaml::node` 看起来像值类型（含 `yaml::document m_document` 字段 + caller 按值返回 `add_map() / add_seq()`），实际是引用类型：

   - `m_node`（`c4::yml::NodeRef`）是真正工作字段——所有 ryml 调用通过它转发
   - `m_document` 字段在原版**从未被 m_node 引用**，仅做"假装值类型"的占位（实际是内存浪费的死代码，但 caller 没踩到）
   - 所有 yaml::node 之间通过浅拷贝 m_node 共享 caller 的同一棵 Tree —— 因为 ryml 的 seed/lazy 写入机制（`m_node[csubstr(name)]` 返回 **seed NodeRef**，带 lazy key 表示「将要创建 child」）和 `doc.save()` 输出要求**所有修改打到同一棵 Tree**

2. **修复让 m_node 指向自身 m_document.tree()** 同时打碎两条隐含契约：

   - **seed 信息丢失**：新 ctor 用 `NodeRef(&m_document.tree(), n.id())` 重建时只复制 id，**丢了 seed key**。原 `m_node[csubstr("name")]` 返回的 seed NodeRef 表示"在 parent 下创建 child 'name'"，重建后变成普通指向 parent。`set_value` 时 ryml 找不到对应 child → `_set_val` error → 崩
   - **修改打到副本**：`set_map() / add(...)` 全作用在 m_document 的独立副本上，与原 `doc.m_tree` 完全脱钩。即使不崩，`doc.save()` 输出空文档

3. **半 rule-of-five 比不修更危险**。修复方向定下来后（m_node 指向自身），如果不同时补完整 rule-of-five，编译器默认 by-field 拷贝/赋值会浅拷贝 NodeRef 的 Tree\* 字段，临时对象拷贝路径立即制造悬垂：

   ```cpp
   // scene.cpp:28（实际崩点）
   yaml::node root = doc.root().set_map();  // 临时 A 析构 → root.m_node 悬垂
   root.add("name", "scene");               // 立即 UAF
   ```

   补 rule-of-five 后崩点从 UAF 移到 ryml seed 失败（问题 #2），**两层崩溃叠加**。

4. **「修复假设性 bug 引入真 bug」**。原版 yaml::node 的「m_document 是死代码 + m_node 指外部 Tree」设计虽然内存浪费（每个 node 浪费一份 Tree 副本），但在 caller 全用栈上 document 的姿势下**实际工作正确**。grep 整工程零命中"yaml::node 跨 document 工厂返回"模式 —— **P0-27 描述的悬垂场景在实际代码中不存在**。修复反而让 `Scene::save → Client::init` 直接崩溃。

**事故时间线**：

| 时刻 | 动作 | 结果 |
|---|---|---|
| 上午 | P0-27 第一版修复（只改 ctor），未跑现有功能验证即上报「修复完成」 | — |
| 当晚 | 用户跑 `Client::init` → `Scene::save` | 崩在 `yaml.cpp::node::add` → ryml `_p(node)` error |
| +10 min | 诊断为漏 rule-of-five，补拷贝/赋值/移动 | — |
| +5 min | 用户再跑 | 崩在 `node::set_value` → ryml `_set_val` error（seed 丢失） |
| +10 min | 承认修复方向错误，`git checkout` 回滚两个 yaml 文件 | `Scene::save` 恢复正常 |

**建议**（结论性）：

- **P0-27 改为【不修-误读设计 + 过度防御】**：cat 当前 caller 全部用引用语义（doc 与 node 同栈帧寿命）。修复破坏 `doc.save()` 输出 + 触发崩溃，不可行。
- 真要根治应**删除 m_document 字段**，让 yaml::node 只持 `c4::yml::NodeRef`，明确"引用语义 + caller 管 document 生命周期"。但这是 API 重构，不在 crash-safety 范畴。
- 当前在 yaml.h 加一行注释固化 ownership 契约即可：
  ```cpp
  // yaml::node 持 m_node 引用 caller 的 yaml::document.m_tree。
  // caller 必须保证 document 比所有派生 node 活得久（cat 现有用法天然满足）。
  // m_document 字段保留是历史遗留死代码（曾意图做"自带副本"，但 ryml 的
  // seed/lazy 写入与 doc.save() 链路要求所有 node 共享同一 Tree，副本机制
  // 不可行）。未来如果重构 API，可直接删除 m_document 字段。
  ```

## 二、冗余 — 重复保护 / 死代码 / 仪式性清理

### #3 `KeyFrame_compare_less2` 的 NULL "双保险"（commit `0698ba8`）

```cpp
bool KeyFrame_compare_less2(KeyFrame* const& f1, KeyFrame* const& f2)
{
    // 双保险：addKeyFrame 已挡 NULL，但 binary_search 路径里再防一层
    const uint t1 = (NULL != f1) ? f1->time() : 0;
    const uint t2 = (NULL != f2) ? f2->time() : 0;
    return t1 < t2;
}
```

**问题**：

- 同一 commit 已经在 `addKeyFrame` 入口拒收 NULL，`m_frames` 中**不变量上**不可能出现 NULL。比较器再防一层是死代码。
- `binary_search2` 每次调用要做 O(log N) 次比较，每次比较多 2 个分支 + 2 次 NULL 判断，纯运行时浪费。
- 注释自己写"addKeyFrame 已挡 NULL"，说明作者也知道是冗余，但仍写了，正是 review 总报告 §4 想消除的"防御性偏执"。

**建议**：删除 NULL 兜底，仅保留 `return f1->time() < f2->time();`；不变量靠 `addKeyFrame` 单点强制。

### #4 `AnimationChannel::update` 重写后的 midFrame NULL 兜底（commit `0698ba8`）

```cpp
KeyFrame* midFrame = frames[mid];
if (NULL == midFrame)
{
    _resetTransform();
    return;
}
...
if (NULL == pBefore || NULL == pAfter)
{
    _resetTransform();
    return;
}
```

**问题**：

- 与 #3 同源：`m_frames` 不变量保证非 NULL，这两处兜底永远不会触发。
- 每帧每 channel 加 3 个 NULL 比较 + 2 个 early return 路径。
- 原函数 41 行重写到 79 行，**4 处 `_resetTransform()` + 2 处 `_set` early return**，控制流远比"二分→分支→插值"原模型复杂。

**update 真正需要修的只有 3 行**（与 review 报告 Warning 级原话一致）：

| 原 BUG | 最小修法 |
|---|---|
| `assert(mid < frames.size()-1)` release 失效后越界写 | `if (mid + 1 >= frames.size()) { _set(*frames[mid]); return; }` |
| `after.time() == before.time()` 除零 | `if (after.time() == before.time()) { _set(after); return; }` |
| `KeyFrame zero;` 未按 type 初始化 | `KeyFrame zero; zero.clear(m_type);` |

**建议**：恢复原"二分+三分支"结构，只插入上面 3 处守护；删除 midFrame NULL / pBefore-pAfter NULL 兜底。

### #5 `Object::s_objectIDMapReleased` 标志 + `safe_delete` 双保险（commit `0698ba8`）

```cpp
static bool s_objectIDMapReleased;   // 新增

void Object::releaseObjectIDMap()
{
    safe_delete(s_objectIDMap);          // 已经把指针置 NULL
    s_objectIDMapReleased = true;        // 再加一个标志
}

ObjectIDMap<Object>& Object::_objectIDMap()
{
    assert(!s_objectIDMapReleased);      // 仅 debug 生效
    if (NULL == s_objectIDMap)
        s_objectIDMap = new ObjectIDMap<Object>;
    ...
}
```

**问题**：

- `safe_delete` 已经把 `s_objectIDMap` 置 NULL，下次进来 `NULL == s_objectIDMap` → lazy-new 出新 map。`s_objectIDMapReleased` 唯一作用就是把 lazy-new 改成 assert。
- assert release 下静默失效，**与 review 总报告 §4 自己点名要消除的反模式一致**：critical 路径用 `assert` 兜底等于没兜底。
- 实际语义是"release 后禁止再用"，应该用 `abort()` 或 `log_fatal` + early return，而不是 debug-only assert。

**建议**：二选一

- 保持 lazy 创建语义，不要新增标志，删掉这个变量。
- 或把 assert 换成 `log_fatal + abort()`，让标志在 release 下也有意义。

### #6 `cat/skin.cpp::m_jointMatricesCapacity` 字段（commit `02e49ab`）

**改动**：新增 `int m_jointMatricesCapacity` 成员，构造/析构对应初始化，`generateJointMatrix` 内 lazy realloc。

**问题**：

- 同一 commit 上游 `setInverseBindMatrices`（`3df3ecb` 已加）**已经在 IBM 变化时 `safe_delete_array(m_jointMatrices)`**，下次进 `generateJointMatrix` 走 `NULL == m_jointMatrices` 分支自然重建。
- 容量字段唯一覆盖的场景是「joints 增长但 IBM 不变」—— 当前 `Skin::addJoint` 没有 reset jointMatrices 的实现，但这本身是 addJoint 的契约问题，应该在 `addJoint` 里同样 `safe_delete_array(m_jointMatrices)`，而不是引入"容量字段+对比扩容"的状态机。
- 多一个字段 = 多一个不变量要维护（`count == 0 ⟺ ptr == NULL ⟺ capacity == 0`），未来很容易漏掉。

**建议**：删除 `m_jointMatricesCapacity`；在 `addJoint` 同步 `safe_delete_array(m_jointMatrices)`（与 `setInverseBindMatrices` 对齐）。

### #7 `cat/gltfLoader.cpp` 中 `size_t > INT_MAX` 截断守卫（commit `02e49ab`）

```cpp
if (data->attributes_count > static_cast<size_t>(INT_MAX) ||
    NULL == data->attributes[0].data ||
    data->attributes[0].data->count > static_cast<size_t>(INT_MAX))
{
    log_error("_flattenVertexAttrs invalid count: attr=%zu, vertex=%zu", ...);
    assert(false);
    return NULL;
}

if (timeAccessor->count > static_cast<size_t>(INT_MAX) ||
    timeAccessor->count != frameAccessor->count) { ... }
```

**问题**：

- `INT_MAX ≈ 21 亿`。GLTF 单 primitive 的 attribute 数（通常 < 16）、单 mesh 顶点数（最多千万级）、单动画通道关键帧数（最多几千）都**根本到不了这个量级**。这些守卫在生产环境永远不会触发。
- 引入了对 `<limits.h>` 的依赖、8 行错误处理代码、`log_error` 字符串常量，全是噪音。
- review 文档原话只是 Warning 级"属性名很短，OK，但容易踩坑"，**不是 Critical**。

**建议**：

- 删除所有 `> INT_MAX` 守卫。
- 真要做防御就在 cgltf 加载入口（cgltf 校验返回值）一次性挡，不要在每个 helper 里散落 8 行模板代码。
- 如果担心 size_t→int 截断，用 `assert(count <= INT_MAX)` 即可，无需 release fallback。

### #8 `~Animation` / `~AnimationChannel` 中的 `clear()` 调用（commit `2049f99`）

```cpp
Animation::~Animation()
{
    for (int i = 0; i < m_channels.size(); ++i)
        safe_delete(m_channels[i]);
    m_channels.clear();      // 新增
}

AnimationChannel::~AnimationChannel()
{
    for (int i = 0; i < m_frames.size(); ++i)
        safe_delete(m_frames[i]);
    m_frames.clear();        // 新增
}
```

**问题**：

- 析构函数最后一行调 `m_channels.clear()` / `m_frames.clear()`，**下一行就是 `~varray()`**，varray 自己会清。

**建议**：删除两处 `clear()`，保留 `safe_delete` 循环；如果想强调"指针已释放"，加一行注释即可。

### #9 `Animation::addChannel` 入口 NULL 拒收（commit `2049f99`）

```cpp
void addChannel(AnimationChannel* c) { if (NULL != c) m_channels.push_back(c); }
```

**问题**：

- review 文档明确这一条是 **Suggestion 级**（最低），不是 Warning。
- 仅有的 caller `GltfLoader::_loadAnimation` 在同一 commit 已经在失败分支 `safe_delete(channel) + continue`，不会传 NULL 给 addChannel。

- 要么改 `assert(NULL != c);` 让外部错误调用 fail-loud。
- 不要"silently 吞 NULL"——这与 review 总报告 §4 批评的"assert 静默失效"语义对偶。

### #10 `02e49ab` 与 `04dde69` 对 `alloc_id` 的两次重叠修改

**改动**：

- `02e49ab` 加 `if (m_id >= INT_MAX - 1) { assert(false); return -1; }`
- `04dde69` 把 `++m_id` 改 `scl::atomic_inc(&m_id)`，溢出守卫改写为 `if (newId <= 0)`

**问题**：

- 两次 commit 在 4 小时内对同一函数体改了两次，第二次几乎重写了第一次的全部内容。
- `02e49ab` 把 `add()` 入口也加了 `if (obj->id() < 0) return;`——这条逻辑是 `alloc_id` 返回 -1 之后下游兜底。两次提交合在一起留下三层重复的"id < 0/溢出"保护。

**建议**：

- 既然 `04dde69` 是错的（参见 #1），回滚之后只保留 `02e49ab` 的 `INT_MAX - 1` 单点检查；`add()` 入口的 `obj->id() < 0` 兜底可以保留作单点防御。

## 三、可读性 / 风格 / 微优化

### #11 `child(int)` / `Scene::object(int)` 改成"范围外返回 NULL"（commit `02e49ab`）

```cpp
Object* child(int index) { return (index >= 0 && index < m_childs.size()) ? m_childs[index] : NULL; }
```

**问题**：

- cat 风格规则 §1.5：「**不抛异常；用返回值 + `assert()`/`scl::assert.h` 检查不变量**」。范围检查本属 caller 契约，应该 `assert(index >= 0 && index < m_childs.size())`，不该把 silent NULL 当默认行为。
- 修改后所有 caller 都得加 NULL 判断（实际并没改 caller）。原代码可能崩，新代码会沉默地传一个 NULL 到下游再崩，问题被推到更难追的地方。
- review 总报告 §4 反复批评的就是这种"错误静默化"。

**建议**：

```cpp
Object* child(int index) { assert(index >= 0 && index < m_childs.size()); return m_childs[index]; }
```

风险用 debug assert 暴露，hot path 不带分支；release 下契约违反崩与不崩是一样的。

### #12 `KeyFrame` / `AnimationChannel` 把 `union` 改 `struct`（commit `2049f99`）

**改动**：

```cpp
// 原
union { scl::quaternion m_rotate; scl::vector3 m_move; scl::vector3 m_scale; };
// 改后
scl::quaternion m_rotate;
scl::vector3    m_move;
scl::vector3    m_scale;
```

**问题**：

- 这是 review **Critical 级**的真 UB 问题，必须修，方向无误。
- 但 `KeyFrame` 是动画系统里实例数最多的类型——一条动画几十 channel × 每 channel 几百 keyFrame = **数万实例**。每实例多 `sizeof(quaternion) + sizeof(vector3) ≈ 28` 字节（取决于内存对齐）。50 个动画 × 10000 帧 = 500K 实例 × 28 = **额外 14MB 内存**。
- UB 的真正成因是**构造函数依次 clear 三个非活跃成员**，不是 union 本身。更精确的修法是构造只 clear 当前 type 的成员（或者 `memset` 整块 union 来回避 active member 语义）。

**建议（如果内存敏感）**：保留 union，把构造改为：

```cpp
KeyFrame() : m_time(0)
{
    memset(&m_rotate, 0, sizeof(m_rotate));   // 整块清零，绕开 active member 语义
}
void KeyFrame::clear(KEY_FRAME_TYPE type)
{
    switch (type) { ... 只 clear 对应成员 ... }
}
```

`memset` 对 trivially copyable 类型不算 UB，且单次清零等价于覆盖 union 全部成员，下次按 type 切换时直接赋值即可。

**如果项目内存不敏感**（当前 cat 是学习/实验引擎，14MB 不致命），现状的 struct 写法也可以接受，但建议在头文件加一行注释说明取舍。

### #13 `0698ba8` 中 `objectByName`/`childByName` 加 `recursive=true` 默认参数

**评估**：本条**不是过度防御**，是合理的接口规范化（参见 `cat代码风格.mdc §3.18`）。仅提醒一点：默认值 `recursive=true` 与之前的隐式递归行为兼容，但 review 报告里没有要求这条变更；属于"顺手做的规范活"，从代码风格规则看是允许的。

## 五、共性反思

### A. "双保险"是 review-driven fix 最大的隐性成本来源

集中体现在 #3 / #4 / #5 / #9：上游已经在入口挡了不变量违反，下游又在每次使用前再 NULL/越界判一次。结果：

- **死代码堆积**：永远不会触发的分支，但每个 hot-path 调用都要走。
- **不变量边界模糊**：未来读者不知道"NULL 是否可能"，又会再加一层。
- **assert 在 release 下静默失效**——这是 review 总报告 §4 自己点名要消除的反模式，结果修复时反而引入了更多。

**经验法则**：

> 同一不变量只在**唯一一个**地方强制（入口 / 构造 / setter）。其它地方相信不变量、必要时用 `assert` 暴露违反，**不要再加 release-active 的兜底**。

### B. assert 与 release fallback 是两种东西，混用就两边都没用

`#5`（`s_objectIDMapReleased`）、`#11`（`child(int)` 范围检查）都把"调用契约违反"和"运行期可恢复错误"混在了一起：

- 契约违反应该 `assert + abort` 或 `log_fatal + abort`，让问题立刻暴露；
- 可恢复错误应该明确 fallback 路径 + log_warning，但 hot path 慎用。

review 总报告 §4 已经把这条作为系统性问题列出，**修复时不要在同一个函数里既写 `assert(false)` 又写 `return NULL/identity` —— 那等于 debug 崩、release 静默错，最坏的两个世界。**

### C. AGENTS.md / 代码风格规则是"修复决策"的硬约束，不是参考

`#1`（ObjectIDMap 加锁）直接踩了 AGENTS.md §7 的"单线程"红线。修复者显然读了 review 文档，但没读项目约定文档。**review 中标"线程"维度的问题，在单线程项目里默认就该是"加注释 + 文档化"，不该是"加锁"。**

### D. cgltf / 外部数据校验应在唯一一处做

`#7`（INT_MAX 守卫）说明：cgltf 加载链路的每个 helper 都自己写一遍"size_t→int 安全"检查会迅速产生噪音。应该在 `cgltf_parse_file → cgltf_load_buffers` 之后立刻做一次完整的 cgltf 数据校验（顶点数、attr 数、accessor 类型、buffer 非空），下游 helper 假设输入合法。

### E. 内存/性能成本要在修复时被显式计算

`#12`（union → struct）改动安全，但 14MB 的内存代价没在 commit 注释里讨论过。**修复 Critical UB 之前应该评估替代方案的代价**——这次是 14MB，下次可能是 50%的 CPU 退化。

### F. 「难看的代码 ≠ 错的代码」：动 ctor / 拷贝 / 赋值前必须先看 caller 实际用法

`#14`（yaml::node 修「悬垂」）暴露的最贵教训。当看到看起来浪费、死代码、风格丑陋的字段或语义时，**先 grep 看 caller 怎么用、看实际行为是否依赖这种"丑陋"，再决定动不动它**。让 API "名实相符"可能正是打碎 caller 实际依赖的 implicit contract。

具体：

- yaml::node 的 `m_document` 字段**看起来**是值类型的标志（深拷贝 Tree → 自带副本），但 grep 全工程零命中跨 document 寿命的工厂用法。**实际是 m_node 指外部 Tree + m_document 是死代码副本**的引用语义。我按"值类型"假设修 ctor，结果打碎隐含的「引用 caller's document」契约。
- 半 rule-of-five 比不修更危险：只动 ctor 不动拷贝构造，相当于在生命周期路径上**留下半通的桥**——临时对象拷贝路径立即制造悬垂，业务代码立即崩。

**经验法则（动核心类型语义之前必做）**：

1. **grep 全部 caller**：实际调用姿势是按值 / 按引用 / 是否跨生命周期？
2. **本地至少跑一次现有功能**验证修复不打碎已工作的路径。光过编译 + lint 不算验证。
3. **rule-of-five 不可半修**：动了 ctor，必须同时审查拷贝构造、拷贝赋值、移动构造、移动赋值、析构是否需要对齐修改。任何一个不一致都会成为新 UAF 入口。
4. **假设性 bug 优先级降级**：review 标的"理论可能发生但 grep 零命中"的悬垂/UAF，优先级低于"加注释固化契约"，不应做侵入式修复。

## 七、给后续 review-driven fix 的建议

1. **修复前先读 `AGENTS.md` 与 `.cursor/rules/cat代码风格.mdc`**：review 报告告诉你"哪里有 bug"，约定文档告诉你"在这个项目里允许怎么修"。两者冲突时以约定为准。
2. **每写一行 release-active 的防御代码，问自己：上游不变量在哪里强制？下游真的可能拿到这个非法值吗？** 如果上游已经挡过，下游的兜底就是死代码 + 性能噪音 + 不变量模糊化。**不变量永远在单点强制，其它地方用 assert 暴露违反**。
3. **动核心类型（ctor / 拷贝 / 赋值 / 移动 / 析构）之前，必须先看完整 caller 用法 + 跑一次现有功能验证**。看起来"难看 / 浪费 / 死代码"的字段可能正承担着 implicit contract（如 #14 yaml::node 的 m_document 是「假装值类型」的占位但 caller 实际依赖 m_node 指外部 Tree 的引用语义）。**修「假设性 bug」之前先 grep 整工程的 caller 模式，零命中的悬垂/UAF 风险应降级为「加注释固化契约」而非侵入式修复**。半 rule-of-five 比不修更危险。
