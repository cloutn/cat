## 一、本文档的位置

`task2.md` § M0.3 给出了 4 条粒度较粗的需求条目：
1. ownership 模型定义
2. typed opaque handle 替换 `void*`
3. ShaderCache 结构化 key
4. SPIR-V 磁盘缓存

本文档把这 4 条拆成可执行的子里程碑、明确"做什么 / 不做什么 / 怎么验收"，并把 SPIR-V 磁盘缓存（原属 M0.3）剥离出去延后处理，理由见 §3.2。

它**不替代** `task2.md`，只是 M0.3 这一格的实施细则。

## 二、目标与不做的事

### 2.1 目标

- 把"谁拥有 / 谁释放 / 谁只是借用"这件事在代码里**可静态识别**，而不是只活在脑子里。
- `IRender` 接口对外暴露的句柄从 `void*` 改成 typed opaque handle，让"把 Texture 当 Buffer 释放"这类错误在编译期就挡住。
- `ShaderCache` 的查找 key 从字符串拼接改成结构化、顺序无关，避免重复 permutation 与字符串构造开销。
- 给后续 Phase 3（Jolt 物理）扫清最大的硬技术依赖：物理体与渲染体引用统一用 ID/handle，而不是裸指针。

### 2.2 明确不做的事

- **不做**完整的 RAII / TRefCountPtr 智能指针体系。保留 `Env` 已有的 "find + ref count + release" 风格（`env.cpp:62-110`），避免改造面失控。
- **不做**真正的 RHI 重抽象。`IRender` 仍然是当前形态，只是参数类型换骨。
- **不做** M0.4 的 Transform dirty flag / frustum culling / FrameStats。那是独立里程碑。
- **不做**资源序列化层（GUID/path 引用）。Phase 1 的材质系统再处理。
- **不做** SPIR-V 磁盘缓存（见 §3.2）。

## 三、当前状态盘点

### 3.1 已经做对的部分

- `Env::getTextureFile` / `releaseTextureFile`（`cat/env.cpp:62-110`）已经实现"路径命中复用 + ref count + 归零销毁"。这是整个 M0.3 风格的样板，其他资源类型可以照抄。
- `Shader` 的设备句柄析构走 `m_render->releaseShader(m_deviceShader)`（`cat/shader.cpp:132-139`），生命周期闭环正确，只是 `m_deviceShader` 仍是 `void*`。
- `Primitive::release` 正确处理了"多个 attr 共享同一 vertex buffer"的去重释放（`cat/primitive.cpp:131-163`），ownership 语义实际上是 unique，符合 §4.1 的模型。

### 3.2 SPIR-V 磁盘缓存为什么从本里程碑剥离

`task2.md` 原文把它列在 M0.3，理由是"和 ShaderCache 结构化 key 一脉相承"。本计划决定剥离，理由：

1. **优先级错位**：M0.3 的核心价值是"把 ownership / handle 砸实"，物理接入和编辑器稳定性都吃这一块；磁盘缓存只解决"冷启动慢"，属性能优化。
2. **依赖更下游的东西**：磁盘缓存的 key 至少要含 `{vsPath, psPath, macroSetHash, includeMtime, shaderc 版本}`，其中 include 展开和 mtime 校验在当前 `_loadfile` 形态下要么不准确要么强耦合，一动就连带改 `cat/shader.cpp` 的 macro 注入逻辑（已在 `代码审查-Shader.md` § 2.1 标为 Critical）。
3. **风险大于收益**：磁盘缓存写错会导致"看似正常的二次启动用了旧 SPIR-V"，这种 bug 比"每次启动多 200ms 编译"难 N 倍。
4. **更合适的时机**：Phase 1（光照）落地后 shader 数量会爆，那时再做磁盘缓存收益最大。

**新归属**：放进 Phase 1 末的"M1.5 材质系统整理"之后，作为 Phase 1.5 的小尾巴，或单列为 M0.6。本文档先记一笔，不展开。

## 四、设计：ownership 模型

### 4.1 三类资源的 ownership

| 类别 | 资源 | ownership | 落地形式 |
|---|---|---|---|
| **Unique** | Vertex Buffer、Index Buffer、Mesh CPU data | 单一 owner，owner 析构即销毁 | `Primitive` 直接持有，`~Primitive` 调 `releaseXxx` |
| **Shared + RefCount** | Texture、ShaderModule、Pipeline、UBO Layout | 多 owner，命中复用，归零销毁 | 由 `Env`（或将来 `RenderResourceCache`）集中管 |
| **Non-owning view** | Material 引用 Texture、Primitive 引用 Material/Shader、Object 树父子引用 | 仅读，不负责生命周期 | 保留裸指针 / handle，**不**调 release |

### 4.2 落实方式

- **Unique** 类不引入新机制，沿用 `Primitive::release` 已有写法，只是把 `void*` 换成 `BufferHandle`。
- **Shared** 类全部经过 `Env::getXxx / releaseXxx` 单一入口。当前只有 Texture 走这条路，本里程碑**只补 ShaderModule 这一条**（用 `ShaderCache::getShader` 做命中即可，本身已经有去重，但缺 ref count）。Pipeline / UBO Layout 因为目前还在 `VulkanRender` 内部 hash_table 缓存，不外露给 cat 层，**不**纳入 M0.3。
- **Non-owning** 类强制约定：拿到 handle 不调 `releaseXxx`。靠注释 + code review 保证，本里程碑**不**引入 borrow checker。

### 4.3 一条强制规范

> `cat` 层禁止任何代码持有渲染设备资源的"裸指针副本"。所有持有都必须经过对应的 `getXxx` 走 ref count + 句柄。
> 仅 `Material::release` / `Primitive::release` / `Shader::~Shader` 三个收口点可以调 `releaseXxx`。

这条规范进 `AGENTS.md` 的"接口与依赖约束"段。

## 五、设计：opaque handle

### 5.1 形态

```cpp
namespace cat {

struct TextureHandle
{
    uint32 id;
    bool   isValid() const { return id != 0; }
    bool   operator==(TextureHandle r) const { return id == r.id; }
    bool   operator!=(TextureHandle r) const { return id != r.id; }
};

struct BufferHandle { uint32 id; bool isValid() const { return id != 0; } /* ... */ };
struct ShaderHandle { uint32 id; bool isValid() const { return id != 0; } /* ... */ };

const TextureHandle TEXTURE_HANDLE_INVALID = { 0 };
const BufferHandle  BUFFER_HANDLE_INVALID  = { 0 };
const ShaderHandle  SHADER_HANDLE_INVALID  = { 0 };

} // namespace cat
```

要点：
- 三个 handle 类型**互不可转**，编译期挡住"把 Texture 当 Buffer 释放"。
- `id == 0` 一律表示无效，所有 `releaseXxx` / `bindXxx` 都允许收到无效 handle 直接 no-op（对齐 `safe_delete` / `vkDestroyXxx` 的语义）。
- handle 是 trivially copyable + POD，可以无脑值传递，不引入引用计数到 handle 本身。引用计数仍由 `Env` / `VulkanRender` 在内部表里维护。
- 不放在 `cat/` 命名空间下的子目录，统一放 `catbase/cat/handle.h`，因为 `IRender.h` 在 `catbase/` 必须能 include 到。

### 5.2 池子在哪里

handle → 实际 `VkBuffer / VkImage / VkShaderModule` 的查表在 `VulkanRender` 内部，cat 层不可见：

```cpp
// catvulkan/cat/handlePool.h（VulkanRender 私有）
template <typename TResource>
class HandlePool
{
public:
    uint32  alloc(TResource&& r);   // 返回非 0 id
    void    free (uint32 id);
    TResource*       get(uint32 id);
    const TResource* get(uint32 id) const;
};
```

要点：
- **不引入 generation 字段**：当前单线程、句柄严格成对申请释放，generation 是"防 use-after-free"的额外保险，本里程碑不上，避免过度防御（参考 `doc/review/代码审查-反思-过度防御与冗余修改.md` 的取舍）。
- 内部用 `scl::varray<TResource>` + free list，0 号 slot 永远空着当 sentinel。
- `HandlePool` 不出现在 `cat/`、不出现在 `catbase/`，**只**在 `catvulkan/` 内部。这条对应 `AGENTS.md` 现有规则"cat 不 include vulkan/...""。
- 单线程，**不加锁**。如果未来要多线程，在这里加 `scl::spinlock` 即可，对外接口不变。

### 5.3 失效与诊断

- `releaseXxx(INVALID_HANDLE)` no-op，不 assert。
- `releaseXxx` 收到已释放 handle：debug 走 `assert(false)`，release 走 no-op。靠 free list 标记位识别"slot 当前是空闲"，是最便宜的检查。

## 六、设计：ShaderCache 结构化 key

当前实现的两个具体毛病（来自 `代码审查-Shader.md` § 2.3）：
1. **key 顺序敏感**：`add("NORMAL")` + `add("TEXTURE")` 与反序得到不同 key、编译两次、占两份缓存。
2. **每次都构造长字符串走 `scl::tree`**：cache 命中也要付字符串构造 + 平衡树查找开销。

### 6.1 新 key 形态

```cpp
struct ShaderKey
{
    uint32 vsPathHash;          // FNV-1a 32 of vsFilename
    uint32 psPathHash;          // FNV-1a 32 of psFilename
    uint64 macroSetHash;        // 见 6.2

    bool operator==(const ShaderKey& r) const { /* ... */ }
};
```

- `vsPathHash` / `psPathHash` 用 32-bit FNV-1a。冲突概率对项目规模（< 100 个 shader 文件）完全够。
- `macroSetHash` 用 64-bit。

### 6.2 macroSet 的 canonical 化

构造 macroSetHash 之前：
1. 拷贝 macro 数组到临时 `scl::varray<ShaderMacro>`。
2. 按 `name` 字符串字典序排序。
3. 顺序 hash：每个 macro 把 `name + "=" + value` 喂给 FNV-1a。

排序确保"宏集合相同则 hash 相同"，杀掉 permutation 重复。

### 6.3 容器

`scl::tree<String, Shader*>` → `scl::hash_table<ShaderKey, Shader*>`。
若 `scl::hash_table` 不支持自定义 key 哈希函数，本里程碑顺手加一个特化（独立小补丁，不入 M0.3 主 PR）。

### 6.4 ShaderModule 的 ref count

当前 `ShaderCache` 命中即返回同一个 `Shader*`，**没有 ref count**。`~ShaderCache` 一把 delete 所有 shader，依赖"shader cache 活到进程结束"这个隐性假设。Phase 3 物理引入后这个假设仍然成立，**本里程碑不加 ref count**，只把这条假设写进 `Env / ShaderCache` 的头注释。

如果以后要支持"卸载场景 → 释放未用 shader"，再在 `Shader` 上加一个 `int m_refcount` 即可，是向前兼容改动。

## 十一、学习笔记交付

`doc/学习笔记/资源-ownership-与-handle.md` 应包含：

1. **三类 ownership 模型**的工程动机（不是抄定义，写自己踩过的坑）。
2. **typed opaque handle vs 强类型指针**的取舍：为什么没用 `class Texture* texture` 这种引用对象指针。
3. **UE `FRHITexture` / `TRefCountPtr`**对照：UE 走的是引用计数智能指针，cat 走的是 handle + 中心化 pool；两者的边界与适用场景。
