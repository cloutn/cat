## 一、cat 的错误处理哲学

按严重度从轻到重，对所有错误用四档工具：

| 档 | 含义 | debug 行为 | release / shipping 行为 |
|---|---|---|---|
| **warning** | 一般问题，无需调试关注 | 写日志 | 写日志，继续 |
| **ensure**（可继续的错误） | 契约违反但**可以继续运行** | 调试器附着时中断（int 3），写日志，返回 false | 写日志，返回 false，**caller 决定后续** |
| **assert**（不可继续的错误） | 契约违反且**不可继续运行** | 中断（int 3） | 走终止路径（log + throw / exit） |
| **fatal**（仅 verbosity 等级） | 高优先级日志，本身**不强制中断** | 写日志 | 写日志，继续 |

四档同时遵守三条规则：

1. **debug 期一定要让开发者看到**：在错误代码点中断（int 3 / `PLATFORM_BREAK`），不抛 C++ 异常、不展开栈——保留现场让调试器停在原地。
2. **release 期是否继续，由 caller 决定，不在错误源头写死**：错误源只负责"暴露 + 留信号"，可恢复性是 caller 上下文相关的，**同一段错误代码可能被多个 caller 调用，对每个 caller 可恢复性不同**。
3. **工具表达意图，不依赖每次判断**：写"必死"用 assert，写"可恢复"用 ensure，让代码 review 一眼能看出作者的意图。

## 二、UE 的 `check / ensure / Fatal` 极简提炼

UE 5.6 `AssertionMacros.h` 把哲学落成三档（去掉变体和格式化）：

**`check(expr)` — 不可恢复**

```cpp
#define UE_CHECK_IMPL(expr) \
    if (UNLIKELY(!(expr))) \
    { \
        if (FDebug::CheckVerifyFailedImpl2(#expr, __FILE__, __LINE__, TEXT(""))) \
            PLATFORM_BREAK(); \
        CA_ASSUME(false); \
    }
```

- `DO_CHECK = 0`（默认 Shipping）下整个宏编译为空——零成本
- 失败 → 写日志 + `PLATFORM_BREAK()` → 走 SEH unhandled exception filter → CrashReportClient → 进程终止
- 无返回值——失败就是 fatal，没"可继续"的语义

**`ensure(expr)` — 可恢复**

```cpp
#define UE_ENSURE_IMPL(Always, InExpression) \
    (LIKELY(!!(InExpression)) \
        || (::UE::Assert::Private::ExecCheckImplInternal(...bGEnsureHasExecuted..., #InExpression) \
        && BreakAndReturnFalse()))
```

- 求值表达式，**始终返回 bool**——caller 拿到 false 决定走什么路径
- 失败 → 写日志 + 调试器附着时 break（**仅第一次**，靠 `std::atomic<bool>` 去重，避免 hot path 每帧炸）+ 继续执行
- `DO_ENSURE = 0`（默认 Shipping）下退化为 `(LIKELY(!!(expr)))`——**只求值表达式、不写日志、不 break，纯返回 bool**

UE 自己的用法说明（`AssertionMacros.h:358-368`）讲清楚了为什么有 ensure：

> Using ensure() here will force a crash report to be generated **without crashing the application** (and potentially causing editor users to lose unsaved work).

**`UE_LOG(..., Fatal, ...)` — 真正的 fatal**

走 `FDebug::AssertFailed` → `FPlatformMisc::RaiseException(EXCEPTION_ASSERT)` → CrashReportClient → 终止。**任何 build configuration 下都触发**（Shipping 也是），独立于 `check/ensure` 的开关。

## 三、Unity 的 `Assert / FatalErrorMsg / ErrorString` 极简提炼

Unity 把"等级"做成 **flag 位组合**（`LogAssert.h:21-43`）：

- `kError` = 1<<0：错误，写日志
- `kAssert` = 1<<1：assert 失败
- `kFatal` = 1<<4：**写日志 + 触发 break**
- `kReportBug` = 1<<15：bug-report 弹窗

落地（`LogAssert.cpp:958-963`）：

```cpp
if (data.mode & kFatal)
    __debugbreak();   // Windows
    // raise(SIGTRAP) on POSIX
```

宏组合（`LogAssert.h:171-174`）：

```cpp
#define FatalErrorMsg(...)  DebugStringToFile(Format(__VA_ARGS__), ..., kError | kFatal)
#define ErrorString(x)      DebugStringToFile(x, ..., kError)              // 只写日志，不 break
```

Unity 的 `Assert(expr)` 在 release 下完全剥除（`ENABLE_ASSERTIONS = DEBUGMODE`），等同 C `<cassert>`，**与 cat 的 scl::assert 设计不同**。Unity 的真 fatal 路径走 `FatalErrorMsg`。

注释里明说语义（`MemoryManager.cpp:1530`）：

> `FatalErrorMsg` effectively aborts the program execution.

但实现刻意用 `__debugbreak()` 而不是 `abort()`——理由：`abort()` 走 SIGABRT，部分调试器停位不准、minidump 信息不全；`__debugbreak` 抛 `EXCEPTION_BREAKPOINT`，SEH 接住后可以保留完整调用栈生成 minidump。

## 四、提炼出能用的设计点

从 UE / Unity 共同的做法里抽出四条，全部适用于 cat：

1. **三档清晰分离**：可恢复 ensure / 不可恢复 assert / 仅日志 warning。fatal 是触发器（break），不是单独等级。
2. **release 期不抛 C++ 异常**：用 break + SEH（Windows）或 raise(SIGTRAP)（POSIX），让 crash handler 接住生成 minidump；**不展开栈、不破坏现场**。
3. **ensure 必须有去重**：hot path 上每帧 break + 写日志会把日志和性能都炸掉。UE 用 `std::atomic<bool>` 去重（每个 callsite 一份），cat 单线程可以直接 `static bool`。
4. **shipping 下 ensure 退化为纯求值**：UE `DO_ENSURE = 0` 时 `ensure(x)` → `(LIKELY(!!(x)))`，零成本。cat 用宏控制。

### 5.2 实际使用模式（grep 采样）

仓库内 `assert(false); return ...;` 是最常见模式：

- `catvulkan/cat/vulkanRender.cpp`：13 处 `assert(false)`
- `cat/gltfLoader.cpp`：21 处
- `cat/primitive.cpp`：4 处 `assert(false); return;`
- `cat/object.cpp`、`catbase/cat/yaml.cpp`、`cat/env.cpp` 等都有

样本（`cat/primitive.cpp:83-85`、`cat/object.cpp:137-139`）形态一致：

```cpp
assert(false);
return scl::matrix::identity();
```

或：

```cpp
assert(false);
return;
```

**这里有个隐含矛盾**：

- 写代码的人在 `assert(false)` 之后**写了 fallback return** —— 说明心智上预期"如果 assert 没让进程崩，业务也要能返回"
- 但 cat 当前 `assert` release 路径是 `throw 1`，主循环没装 `SCL_ASSERT_TRY/CATCH`（搜遍仓库只有 `scl/task_thread.cpp` 和 `scl/log.cpp` 的 worker 线程装了，cat 主循环没装），**实际 release 下 throw 1 沿栈一路到 main 外 → std::terminate → 进程崩**，return 永远不可达。

**结论**：开发者实际写的是 ensure 语义（"违反 + caller 接住继续"），但用了 assert 工具（语义是 fatal）。**这种 mismatch 在 cat 普遍存在**，需要补一档 ensure 给开发者表达"我这里其实是可恢复的"。

### 5.3 与项目代码风格的一致性

`.cursor/rules/cat代码风格.mdc` §1.5：

> **不抛异常**；用返回值（`bool` / `int` / `NULL` 指针）报错；用 `assert()` / `scl::assert.h` 检查不变量。

`scl::assert` release 路径的 `throw 1` 是与这条规则**直接冲突**的历史实现——它只是用 throw 作"崩出去"机制（让 SEH 接住），不是给业务用的可恢复异常。该 throw 应被理解为"内部实现细节，调用方不要 catch"。

补 ensure 后，业务路径用 `ensure` 走"返回 false → caller 决定"，**不依赖异常**，与 §1.5 一致。

### 6.1 `ensure` —— 唯一新工具

放 `free/scl/assert.h`：

```cpp
namespace scl {

// ensure 失败时调用：写日志（走 scl::log 正常通道，不走 urgency_log）；
// 返回值表示"是否建议宏侧触发 break"（debug 期 + 调试器附着时为 true，其它为 false）。
bool ensure_failed(
    const char* const file,
    const char* const func,
    const int line,
    const char* const expr);

} //namespace scl

#ifdef ensure
#undef ensure
#endif

#ifdef SCL_WIN
#define ensure(expr) \
    (!!(expr) || ([&]() -> bool { \
        static bool s_logged = false; \
        if (!s_logged) \
        { \
            s_logged = true; \
            if (scl::ensure_failed(__FILE__, __FUNCTION__, __LINE__, #expr)) \
                __debugbreak(); \
        } \
        return false; \
    }()))
#endif

#if defined(SCL_LINUX) || defined(SCL_APPLE) || defined(SCL_ANDROID) || defined(SCL_HTML5)
#define ensure(expr) \
    (!!(expr) || ([&]() -> bool { \
        static bool s_logged = false; \
        if (!s_logged) \
        { \
            s_logged = true; \
            scl::ensure_failed(__FILE__, __FUNCTION__, __LINE__, #expr); \
        } \
        return false; \
    }()))
#endif
```

### 6.2 何时用 ensure / 何时用 assert（判别原则）

**单条判别**（够用 90% 场景）：

> 想象 release 下这条违反：
> - 当前调用栈上**能定义出合理的兜底**（早退、跳过、用默认值），且兜底后**进程状态仍然有意义** → `ensure`
> - **没有兜底，或继续走会让状态更糟**（UB、数据损坏、内存乱、下游级联崩） → `assert`

换一句话：**"丢掉这次操作，下一帧 / 下次调用还能正常运行"——答得出就 ensure，答不出就 assert**。

**速查表**：

| 错误来源 | 工具 | 理由 |
|---|---|---|
| 外部数据（gltf、yaml、shader 编译、网络包） | `ensure` | 数据不可控，程序应当 robust；丢这个资源不影响其余 |
| 用户/编辑器交互（按钮触发、Gizmo 拖拽、ID 找不到） | `ensure` | 编辑器不能因为一次错误操作崩，未保存数据要保护 |
| 单帧 / 单 draw / 单资源上限超出（MAX_DRAW、MAX_JOINT、command buffer 满） | `ensure` | 丢一帧 / 丢一个 draw 用户能接受；下一帧自动恢复 |
| 可选优化路径失败（descriptor cache 满、pipeline cache miss 后创建失败） | `ensure` | 兜底走 slow path 即可 |
| 程序内部不变量（链表头 NULL、容器 size 为负、双 free、状态机非法转移） | `assert` | 数据结构已被破坏，继续走必然 UB |
| 初始化阶段失败（Vulkan device、必需 shader、主 window） | `assert` | 后续所有代码假设这个东西存在；进程没法跑就该死 |
| switch default 真不可能的分支 | `assert` | 走到这里就是 enum 被写错或内存被踩 |
| 内存/句柄破坏（必需 new 失败、Vk handle 为 NULL） | `assert` | 基础设施崩了，业务层无法兜底 |
| 跨模块契约（IRender 接收 NULL 指针、API 参数越界） | 按场景：能丢这次调用就 `ensure`；契约严重违反就 `assert` | — |

**模糊地带默认 `ensure`**，三条理由：

1. **可升级、不可降级**：ensure 不够强可以包一层 `if (!ensure(x)) { assert(false); return; }`；assert 已经 throw 出去就回不来了。
2. **debug 行为对等**：debug + 调试器附着时 ensure 也 break，**开发期发现错误的能力和 assert 一样**——只在 release 下差异化。
3. **悲观假设**：release 是给用户/玩家用的，编辑器宁可丢一帧也别崩（数据丢更不可接受）。

**反向判别**（防止 ensure 滥用，对应反思 §A 的"silent NULL drop"反模式）：

写 `if (!ensure(...))` 之前问自己一句：

> 如果删掉 ensure 让条件违反**静默 return**，会发生什么？

- 答"下一帧渲染会缺一个物体" → ensure 合适
- 答"数据结构 m_xxx 处于半初始化状态" → 不行，**改 assert**——因为静默 return 后续 caller 会拿到坏数据
- 答"我也不知道会发生什么" → **改 assert**——你都说不出兜底了，不要用 ensure 假装可恢复

### 6.3 用法约定（写入 `AGENTS.md`）

| 场景 | 工具 |
|---|---|
| 一般信息 | `log_verbose / log_debug / log_info` |
| 警告 / 错误，仅留迹，可继续 | `log_warn / log_error / log_fatal`（log 只管 log，等级表达严重度） |
| 错误，**这里其实可继续，但开发期想立刻看到** | `ensure(expr)` |
| 契约违反，**不可继续** | `assert(expr)` 或 `assert(false)` |

判别速查：

- 写 `assert(false); return ...;` —— 大概率是想表达 ensure 语义，应改 `if (!ensure(...)) return ...;`
- 写 `if (NULL == ptr) { log_error(...); return; }` —— 已经是 ensure 模式但手工写，可改 `if (!ensure(NULL != ptr)) return;`

写法规范：

- 推荐 ✅ `if (!ensure(...)) return ...;` 显式早退（多数场景）
- 推荐 ✅ `if (ensure(NULL != ptr)) ptr->do_something();` 通过时执行
- 可用 ✅ `ensure(...);` 不接返回值——仅当 caller 真的不需要走兜底路径，仅作"debug 期暴露 + release 期留日志"的纯检查（debug 期调试器附着仍会 break）
- 避免 ❌ `assert(ensure(...));` 双层断言自我矛盾

### 6.4 日志策略

| 工具 | 日志通道 | 级别 | 理由 |
|---|---|---|---|
| `assert` 失败 | `scl::assert_write` 三路写：OutputDebugString + printf + `urgency_log`（写 `error.log` 立刻 flush） | 无显式 level（视为最高） | assert 之后 `throw 1`，进程可能死——日志线程未必有机会 flush，必须走兜底落盘 |
| `ensure` 失败 | `scl::log::out` 单路（log 系统正常 pipeline + handler） | `LOG_LEVEL_ERROR` | 软失败、进程稳定运行，日志线程能正常 flush；`LOG_LEVEL_ERROR` 与 ensure"可继续"语义对齐，`LOG_LEVEL_FATAL` 留给真正不可恢复的 assert |

## 七、cat 现存 assert 是否符合哲学（review）

按 6.2 约定回看 5.2 的样本：

| 现状 | 哲学评估 | 建议 |
|---|---|---|
| `assert(false); return identity();`（`object.cpp:137`） | mismatch：作者写了 fallback return，意图是 ensure | 改 `if (!ensure(false)) return identity();` —— 但更应该补条件本身（什么导致到这里） |

| `_fillDynamicOffsets` 内 3 处 `assert(false); return 0;` | mismatch：单帧 draw 超限 / 骨骼超限确实可恢复（丢一个 draw 不影响整体） | 改 ensure；diff 里已经做了"_prepareDescriptorSetAndFillData 返回 bool + draw2 早退"——这是正确方向，但底层 `assert(false)` 应该是 `ensure(false)` |

| `vulkanRender.cpp` 13 处 assert | 分两类：①初始化期契约违反（应保留 assert）②draw 路径（应改 ensure） | 按位置二分 |

**整体判断**：cat 现存 assert 用法**60%~70% 实际是 ensure 语义**。补 `ensure` 后逐步迁移，不需要一次全改。

## 九、刻意不做的事

1. **不引入裸 `abort()` / `TerminateProcess`**：GUI 编辑器场景，未保存数据要保护
2. **不引入跨进程 crash reporter**：单人项目，独立可执行体维护成本不值（Unity 的 `UnityCrashHandler.exe` 这种）
3. **不给 log / assert 加锁或 atomic**：cat 单线程契约（`AGENTS.md` §7）
4. **`ensure` 不在 release 下做"仅静默返回 false"的极致退化**（UE Shipping 的做法）：cat 没有 Shipping 这一档，release 就是发布形态，仍然写日志方便事后排查。UE Shipping 退化是为了零成本对齐 console 平台的代码 size 限制，cat 不需要。
5. **不在 `scl/log.*` 内做任何改动**：scl 是单模块单功能哲学，log 只管写日志、不触发中断；ensure 的 break 触发逻辑闭环在 `scl/assert.*` 内完成，对 log 模块零侵入。
