# 02 — 改造难度评估

> 上级：[README.md](./README.md)
> 关心问题：把 cat 的场景层切成"纯 ECS"或"以 ECS 为主干"的工作量、风险、绕不开的硬伤。

## 1. 工作量量级

按"重写一遍场景层"估算（单人节奏，参考 `task2.md` 的工时口径）：

| 模块 | 内容 | 估时 |
|------|------|------|
| ECS 运行时 | Entity 分配 + generation、Archetype / Sparse Set 二选一、view / forEach、System 调度 | 3 ~ 4 周 |
| `scl` 容器配套 | `scl::sparse_set<Entity>`、`scl::archetype_chunk`、type_id 注册表加固 | 1 周 |
| 场景图层级在 ECS 上的重建 | `ParentComponent`、层级 dirty propagation、`globalMatrix` 的 SOA 实现 | 1 ~ 2 周 |
| Mesh / Material / Shader 资产挂载方式重设 | `RenderableComponent` + 资产句柄分离 | 1 ~ 2 周 |
| Skin / Animation 重接 | `SkinComponent`、`AnimationComponent`、target 从 `Object*` / ObjectID 改为 `Entity` | 1 ~ 2 周 |
| 编辑器 / Gizmo / Pick / Save 适配 | Inspector 双源、序列化重写、`registerPickPrimitive` 改 Entity | 2 ~ 3 周 |
| 数据迁移 + 全部回归测试 | 把 Sponza / DamagedHelmet / 现有 demo 跑通 | 1 ~ 2 周 |
| 缓冲（必然超期） | 各种坑、性能调优、回退方案 | 2 ~ 3 周 |
| **合计** | | **12 ~ 19 周（≈ 3~5 个月）** |

横向对照：`task2.md` Phase 0 是 4 周，包含 13 个 critical 修复 + 全部基础设施。**本评估的 ECS 改造工作量是 Phase 0 的 3~5 倍**，相当于把 Phase 1（光照 8 周）整个推迟半年。

## 2. 真正的硬伤（不是写代码量的问题）

工作量是技术问题，硬伤是设计问题。下面这几条不解决，写多少代码都不会变成"对的"ECS。

### 2.1 场景图层级 vs ECS 平铺

ECS 的优势在"组件平铺，cache friendly 批处理"，但场景图天然是**有向树**：

- `globalMatrix()` = `localMatrix * parent.globalMatrix()`，必须沿父链推；
- 子节点的 dirty 必须由父链 dirty 触发；
- 删除父节点要级联删除子节点（OO 析构自动做了，ECS 要显式实现）。

ECS 派的解法是 `ParentComponent { Entity parent; }`，然后做"层级 transform pass"：

```
1. for each entity with DirtyTransform:
       mark its descendants dirty (需要反向索引 child list 或者递归扫)
2. topological order traversal:
       global = local * parent.global
```

问题是：
- 反向索引（parent → children）是个**反 ECS** 的事情，破坏了组件平铺；
- 拓扑遍历的顺序不天然存在 archetype 中，要么动态 sort，要么自己维护层级数组。

UE 的实际做法：`USceneComponent` 直接在 `UObject` 树里走 OO 父子关系，并不走 Mass ECS。Unity 的 ECS 转换流程里 `LinkedEntityGroup` 也是个特殊组件，本质是在 ECS 里夹一个迷你 OO 树。

**结论**：把"场景图层级"装进 ECS，本身就是被 UE / Unity 验证过的"勉强能做但不舒服"的路线。

### 2.2 跨实体引用太多

cat 当前代码里"通过指针 / ID 找另一个对象"的路径：

| 引用源 | 引用目标 | 通过 |
|--------|----------|------|
| `Skin::m_joints[i]` | `Object*` | 直接持指针 |
| `Skin::m_root` | `Object*` | 直接持指针 |
| `AnimationChannel::m_target` | ObjectID（int） | `Object::objectByID` |
| `Env::m_gltfNodeMap` | `cgltf_node* → ObjectID` | `scl::tree` |
| `Mesh::m_parent` | `Object*` | 调试反向引用 |
| `Primitive::m_parent` | `Mesh*` | 调试反向引用 |
| `Env::m_pickPrimitives[i]` | `Primitive*` | 数组下标 |

ECS 化要求：

- 上面所有 `Object*` 改成 `Entity`；
- 所有 `Mesh*` / `Primitive*` 要么也变 Entity，要么作为资产句柄保留 —— 必须做出**统一选择**，不能一半 Entity 一半裸指针。
- `Object::objectByID` 要被 `EntityManager::isAlive(Entity)` + `EntityManager::get<T>(Entity)` 替换，且 generation 需要支持 stale handle 检测。

这是机械工作，但"全栈一刀切"才能保证一致性，否则就是双 ID 系统的噩梦。

### 2.3 资产对象 vs ECS 组件

`Mesh / Primitive / Material / Shader` 是**资产**（共享、引用计数、跨场景复用），不是行为组件。强行把它们 ECS 化（"把每个 Primitive 当 Entity"）会产生：

- 资产被多 Object 共享时，Entity 也要共享 —— 违反 ECS"Entity 是身份"的语义；
- 资产生命周期由 `Env` 管，Entity 生命周期由 `World` 管，两个 manager 必然出现"删 Entity 时该不该 release 资产"的歧义。

业界主流方案是 **"Entity 持资产句柄，资产不进 ECS"**。这没问题，但意味着 ECS 收益主要在"批量更新组件"，而 cat 现阶段没有这种批量更新需求（详见 `03-改造必要性评估.md`）。

### 2.4 编辑器 / Gizmo / Inspector / Save 全是基于 Object*

代码里所有编辑器侧入口都是：

```cpp
Object* m_selectObject;             // testCat/client.cpp
m_selectObject->setMove(...);
m_selectObject->boundingBox();
m_selectObject->save(yaml::node&);
```

迁到 ECS 后这些都要改成：

```cpp
Entity m_selectEntity;
m_world->get<TransformComponent>(m_selectEntity).move = ...;
m_world->get<RenderableComponent>(m_selectEntity).boundingBox(...);
m_serializer->save(m_world, m_selectEntity, yaml::node&);
```

所有面板、Gizmo 状态机、Pick 处理都要重写一遍。这部分量很大且无法分阶段：编辑器是 cat 的主要交互形态，不能"切到 ECS 但编辑器停摆 2 个月"。

### 2.5 现有代码风格规则与 ECS 范式有摩擦

`.cursor/rules/cat代码风格.mdc` 的硬约束：

- 不用 `nullptr` / 不用 STL 容器 / 不用智能指针 / 不抛异常；
- 用 `scl::varray / scl::array / scl::tree / scl::hash_table`；
- 头文件接口不出现 std 容器；
- 头文件优先前置声明，减少传染性 include。

这些规则不阻止做 ECS（`scl` 容器也能做 archetype），但意味着：

- **不能直接抄 EnTT / flecs / Unity ECS** 这些工业级模板库（它们重度依赖 STL + 现代 C++ 异常路径 + 智能指针）；
- 必须用 `scl` 容器从零撸一套，参考资料骤减；
- type_id<T>() 已存在但没有跨 DLL 稳定 ID 设施，未来如果要拆 DLL 还要补；
- 模板代码量增长会冲击"头文件前置声明"惯例（视图 / 系统都是模板）。

### 2.6 析构顺序与全局静态

当前 `ObjectIDMap<Object>` 是全局静态（`cat/object.cpp:25`），`s_objectIDMap` 在 `Object::releaseObjectIDMap()` 显式 release，但 CR 指出"未置 NULL"。这种**全局静态身份服务**是 ECS 化的隐藏地雷：

- ECS 的 `World` / `EntityManager` 应该是**实例对象**（可以同时存在多个 World，例如主世界 + 编辑器世界），不能依赖全局静态 ID 池；
- 改造时必须把 `Object::objectByID` 这种全局入口替换成 `world->get(entity)`，但全引擎几百处调用要一起改。

## 3. 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 切换中长时间编辑器不可用 | 高 | 阻塞 task2 全部 phase | 必须长分支或 feature flag，但单人开发两条线维护代价巨大 |
| ECS 写完之后性能反而劣于 OO（小场景） | 中 | 项目目标偏移 | 先做 micro-benchmark，证明 SOA 收益 |
| 改造期间架构债务回流 | 高 | CR 中已存在的 50+ 项问题被进一步堆叠 | 应先完成 `task2.md` Phase 0，再考虑 |
| 与 Jolt 物理接入决策冲突 | 中 | 已经定的"PhysicsComponent 挂 Object"方案需要重做 | 物理接入暂缓 ECS 化，保留 Object 路径（已是文档结论） |
| 全量回归测试缺位 | 高 | 看不出 regression | 现状没有自动化测试，单人靠手测 |

## 4. 难度结论

| 维度 | 评级 |
|------|------|
| 编码工作量 | ★★★★☆（3~5 个月） |
| 设计风险（场景图 / 资产 / 编辑器） | ★★★★★ |
| 与现有风格规则的摩擦 | ★★★☆☆ |
| 单人可控性 | ★★☆☆☆（需长分支 + 双轨维护） |
| **综合难度** | **极高，相当于"重写场景层 + 重写编辑器接入"** |
