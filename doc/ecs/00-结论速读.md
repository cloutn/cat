# 00 — 结论速读

> 上级：[README.md](./README.md)

## 1. 三个问题的直接答案

| 问题 | 结论 | 信心 |
|------|------|------|
| 改造成 ECS 的**难度**？ | **极高**。保守估计核心运行时 ≥ 4 周，全量数据迁移与外围（编辑器 / 序列化 / 动画 / Skin / Pick）回归 ≥ 2~3 个月。本质上等于"重写一遍场景层"。 | 高 |
| 改造成 ECS 的**必要性**？ | **当前不必要**。task2 路线图（光照 / 阴影 / 物理 / 地形 / 后处理 / 八叉树）全部可在 OO 主干上完成，且 UE / Unity 主线本身也是 OO + Component；ECS 不是当前性能或表达力瓶颈。 | 高 |
| OO 与 ECS **共存**的可能性？ | **非常高**，而且现状本身就是共存雏形（`Scene/Object` + `World/Component`）。推荐保持现状架构，把 `World` 作为"批量同质实体"旁路。 | 高 |

## 2. 一句话推荐

> **不要把 cat 整体迁到 ECS。** 现行的"OO 场景图 + Object 内组件容器 + 旁路 World"已经是 Unity GameObject / UE Actor+Component 的同款套路，是一条被业界验证的低风险路径。把 `cat::World` 留作"未来粒子 / 植被 / Boid / 大量同质实体"的批处理场所即可。

## 3. 执行建议（最小改动）

短期（与 task2 Phase 0 / Phase 3 并行，不立专项）：

1. **不动主干**：`Scene` / `Object` / `Mesh` / `Skin` / `Animation` 全部保持 OO 现状。
2. **完善 Object 组件容器**：
   - 把 `m_fixComponents` / `m_components` 的初始化、生命周期、`addComponent<T>` / `getComponent<T>` / `removeComponent<T>` API 补齐（参考 `doc/物理引擎接入设计与实施计划.md` §3.4 的用法）。
   - 这一步是"OO 框架内的组件化"，不是 ECS。
3. **冻结 `World` 接口表面**：暂时不要让 `World` 渗到 `Object` / `Scene`；让它只在 `main.cpp` 测试位停留，等到出现"批量同质实体"需求（粒子 / 植被 / Boid）时再扩展。
4. **统一 ID 空间（可选）**：让 `cat::Entity` 与 `Object::id()` 共用同一编号池（例如 `Entity = ObjectID`），免得未来桥接时再做双向 map。
5. **`Component` 基类重整**：让 `cat::Component`（`component.h`）变成正式的"Object 用组件基类"，与 `World` 模板里那套数据组件不混在同一个文件；改名或拆文件即可。

中期（出现以下信号之一时再启动 ECS 子项目）：

- 单帧 Object 数 > 5k 且热点在遍历调度而非 GPU；
- 出现"几万植被 / 粒子 / 群体 AI"这类天然 SOA 场景；
- 需要把 transform / animation / physics-sync 写成可并行 system。

长期（永远可选）：

- 即使引入完整 ECS，也建议 **保留 OO 主干** 作为编辑器对外门面（"facade"模式），ECS 只承担批量更新。这是 Unity 走 ECS（DOTS）的实际路径。

## 4. 风险红线

- 不要把 `Object::m_transform` 的"权威所有权"复制到 World 里，否则双数据源会产生同步 bug（这是混合系统最常见的坑）。
- 不要让 ECS 反过来牵动 `Mesh` / `Primitive` / `Material` 的资源所有权 —— 资产仍然由 `Env` + `Object` 持有。
- 不要在没有具体性能 demo 的情况下做 ECS 改造，避免"为了架构而架构"。

更详细的论证见同目录其他文档。
