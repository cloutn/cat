# 01 — 当前 OO 架构剖析

> 上级：[README.md](./README.md)
> 这一篇只描述事实（来自代码 + `doc/子系统-cat.md` + `doc/架构总览.md`），不下结论。

## 1. 现行场景层是一棵纯 OO 树

```
Scene
 └─ scl::varray<Object*>  m_objects     // 顶级节点
       └─ Object
            ├─ Object*               m_parent
            ├─ scl::varray<Object*>  m_childs   (递归子节点)
            ├─ Transform*            m_transform     (延迟分配)
            ├─ Mesh*                 m_mesh
            ├─ Skin*                 m_skin
            ├─ String                m_name
            ├─ int                   m_id            (来自全局 ObjectIDMap<Object>)
            ├─ scl::array<Component*, FIX_COMPONENT_TYPE_COUNT> m_fixComponents
            └─ scl::varray<Component*>  m_components
```

关键观察：

- **强层级**：`Object::globalMatrix()` 沿父链递归相乘，是 OO 场景图的内禀语义（`cat/object.cpp:149-155`）。
- **强身份**：`Object` 通过全局静态 `ObjectIDMap<Object>` 全局唯一可寻；`Object::objectByID(id)` 是动画 / 编辑器 / 拾取的反查入口。
- **资产所有权下沉到 Object**：`Mesh* m_mesh` / `Skin* m_skin` 是裸指针强引用，析构时 `safe_delete`；不通过组件挂载。
- **组件容器已存在但未充分使用**：`m_fixComponents` 是固定槽位（目前只声明了 `FIX_COMPONENT_TYPE_TRANSFORM`，但 `m_transform` 实际上是单独成员，**没有走 m_fixComponents**），`m_components` 是变长数组，目前主流程没有产生过任何 `Component*`。
- **构造时未初始化两个 component 容器**：见 `代码审查-规范.md` 中提到的"`m_fixComponents` 与 `m_components` 未在构造列表里初始化"。

## 2. Mesh / Primitive / Material 是 OO 资源对象

```
Mesh
 ├─ scl::varray<Primitive*>  m_primitives
 ├─ Object*                  m_parent      (调试用反向引用)
 └─ Env*                     m_env

Primitive
 ├─ void**                   m_deviceVertexBuffers
 ├─ VertexAttr*              m_attrs
 ├─ Material*                m_material
 ├─ Shader*                  m_shader
 ├─ Shader*                  m_pickShader
 └─ Mesh*                    m_parent
```

资产对象之间的关系是经典 OO 组合：`Object owns Mesh owns Primitive`。Material / Shader 是从 `Env` 共享拿来的句柄。`Primitive::draw` 直接调用 `IRender::draw2(...)`，没有任何"批量"或"system"的概念。

## 3. Skin / Animation：跨 Object 引用

- `Skin::m_joints` 是 `scl::varray<Object*>`（一组关节节点指针）。
- `Skin::generateJointMatrix(...)` 每帧从这些 `Object*` 调 `globalMatrix()`，与 `m_inverseBindMatrices` 相乘得到 joint matrix，传给 `Primitive::draw`。
- `AnimationChannel::m_target` 是 `int`（ObjectID），通过 `Object::objectByID(id)` 反查；`apply()` 写 `setRotate / setMove / setScale`。

特征：**关节 / 动画通道以 Object* 或 ObjectID 为引用单元**，没有"组件"层；任何替换方案都必须保证这两个反查能继续 O(1)。

## 4. Env：贯穿全场景的全局上下文

`cat/env.h` 持有：

- `IRender* m_render`：向下传递 GPU 后端；
- `ShaderCache* m_shaderCache`：shader 池；
- `m_textureFiles`：`scl::tree<string256, TextureFile>`（按文件名引用计数纹理共享）；
- `m_gltfNodeMap`：`scl::tree<cgltf_node*, int>`（让 Skin 解析时反查到 ObjectID）；
- `m_pickPrimitives`：长度 1024 的拾取表，注册 `Primitive*` → 颜色编码。

**`Env` 是共享资源池 + 加载期临时映射的合体**。任何 ECS 化都要先决定 `Env` 是不是也跟着拆。

## 5. 已有的 ECS 雏形（`World` + `Component`）

代码事实（来自 `cat/world.h`、`cat/world.cpp`、`cat/component.h`、`testCat/main.cpp`）：

```cpp
// catbase/cat/def.h
typedef unsigned int Entity;

enum FIX_COMPONENT_TYPE
{
    FIX_COMPONENT_TYPE_TRANSFORM = 0,
    FIX_COMPONENT_TYPE_COUNT,
};

// cat/world.h
class World
{
public:
    scl::hash_table<uint64, ComponentArrayBase*> m_componentArrayTable;
    int                                          m_entityCounter;

    Entity createEntity();
    template <typename T>
    void   addComponent(Entity e, const T& c);
};

// cat/component.h
class Component { /* 当前为空类 */ };

template <typename T>
class ComponentArray : public ComponentArrayBase
{
public:
    scl::varray<T>      m_components;
    scl::varray<Entity> m_entities;
    void add(Entity e, const T& c);
};

// testCat/main.cpp:33-35  —— 唯一使用点
cat::World  world;
cat::Entity e1 = world.createEntity();
world.addComponent(e1, cat::TestComponent(77));
```

雏形特征：

| 维度 | 现状 | 离工业级 ECS 的差距 |
|------|------|---------------------|
| 实体分配 | 自增 `int m_entityCounter`，无 generation / recycle | 无 entity 删除、无 stale handle 检测 |
| 组件存储 | `hash_table<type_id, ComponentArray<T>>`，每个 T 一桶 | 没有 archetype，跨组件 join 必须线性扫多桶 |
| 查询 / view | 不存在 | 没有 `forEach<A,B>` / 多组件交集 |
| Entity → 组件 索引 | 不存在；`ComponentArray<T>::m_entities` 是 SOA 的"行 ID" | 查"e 是否有 T"需要 O(N) 扫描 |
| System 调度 | 不存在 | 没有 system 概念，没有调度顺序 |
| 与 `Scene/Object` 的耦合 | 完全独立 | 主流程 `Scene::draw` 不经过 `World` |
| 与 `cat::Component`（OO 用）的关系 | 名字撞车但实际无关：`World::ComponentArray<T>` 模板 T 不强制继承 `Component` | 同一 `component.h` 文件里塞了两条不相交线 |

> 备注：`Component` 基类（OO 用）和 `World::addComponent<T>(...)` 模板（ECS 用）当前**虽然写在同一个 `component.h`**，但运行期完全独立 —— `Object::m_components` 持的是 `Component*`，`World` 持的是任意 `T`。这造成了"看起来要统一，但实际上是两套"的尴尬现状。

## 6. 为什么这个雏形长这样

合理推测（不是历史考证）：

- 作者预见到未来需要 ECS，先把 `World / Entity / ComponentArray` 框架占位；
- 主线还没遇到性能或表达力瓶颈，所以雏形没有继续推进；
- `Object::m_fixComponents / m_components` 是 Unity GameObject 风格（Object as Entity），是另一条路；两条路在 cat 中**没有合流，但也没有冲突**。

## 7. 数据所有权 & 析构顺序（这是后续 ECS 化最大的隐性约束）

```
Client owns Scene, Env, Render, World ...
   Scene owns Object[]
      Object owns Mesh, Skin, Transform, Component[]
         Mesh owns Primitive[]
            Primitive references Material, Shader (Env owned)
   Env owns ShaderCache, TextureFile pool, GltfNodeMap, PickPrimitives
   IRender (Vulkan) owns 设备对象（Pipeline / Descriptor / Buffer / Image）
   ObjectIDMap<Object> 是全局静态，析构顺序由静态对象 finalize 决定
```

跨边界点（一旦改 ECS 必须重新设计）：

- `~Object` 递归 delete children（OO 树自然语义）；
- `Skin::m_joints` 持 `Object*`，但不 own；当 Object 死掉，Skin 不知道；
- `Object::releaseObjectIDMap()` 没有置 NULL（CR 已记录）；
- `Env` 贯穿整个加载期，析构在 `Client` 收尾；
- `Animation::m_target` = ObjectID，依赖全局 ID map 还活着。

## 8. 结论

cat 当前是一个 **"OO 场景图 + Unity 风格组件容器（雏形）+ 旁路 ECS 雏形"** 的复合体。OO 是主干，组件机制已经在 `Object` 内部就位（虽然没怎么用），ECS 是站在一旁的占位。这种结构正好对应 Unity 与 UE 已经走过的路线，详细取舍见后两篇。
