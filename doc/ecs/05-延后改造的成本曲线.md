# 05 — 延后改造的成本曲线

> 上级：[README.md](./README.md)
> 关心问题：等 `task2.md` 走完 80% 之后再做 ECS 改造，难度会不会比现在大一个数量级？

## 1. 直接答案

**会。但不是必然的，是"在你不立护栏的前提下"才会到一个数量级。**

更精确地说：

| 路径 | 80% task2 之后做 ECS 的成本 | 相对当前的倍率 |
|------|----------------------------|----------------|
| 失控路径（不立护栏，沿用 OO 习惯写新 phase） | 100 ~ 300 周（≈ 2~6 年） | **8 ~ 20×** |
| 纪律路径（按 04 的护栏建设新 phase） | 24 ~ 50 周（≈ 6~12 个月） | **2 ~ 3×** |

数量级（10×）只在失控路径上成立。纪律路径下，成本曲线是缓慢增长的、可控的，并不会越拖越绝望。

**这意味着：现在的关键决策不是"要不要做 ECS"，而是"要不要在每个 phase 里守住组件化纪律"。**

## 2. 难度增量来自哪里（按 task2 phase 拆）

把 `task2.md` 各 phase 拉成"可能新增的 ECS-relevant 资产"清单，看一下增量从哪里来：

| Phase | 新增内容 | 引入的新组件类型 | 引入的新跨实体引用 | 引入的编辑器面板 | ECS 化代价增量 |
|-------|----------|-------------------|---------------------|-------------------|----------------|
| 0 健康度 | dirty flag、opaque handle、ref-count 资源 | 0 | 0 | 0~1 | **轻微 ↓**（把基础设施修对了反而便宜） |
| 1 光照 | DirectionalLight / PointLight / SpotLight / LightingComponent / Material 扩展 | 4 ~ 5 | 光源 → 阴影目标 view | 2 ~ 3 | 中 |
| 2 阴影 | ShadowComponent / CSM cascade 数据 / 阴影缓存 | 1 ~ 2 | 光源 → 阴影 / 视图 → cascade | 1 ~ 2 | 中 |
| 3 物理 | PhysicsComponent / RigidBodyComponent / CollisionComponent / Trigger | 3 ~ 4 | body ↔ Object、trigger ↔ 受影响 Object | 3 | 中（按物理设计文档已组件化） |
| 4 天空 | Skybox 程序化、太阳和 DirectionalLight 联动 | 1 | 天空 → 主光 | 1 | 轻 |
| 5 地形 | HeightmapTerrainComponent / GrassInstanceComponent / SplatMap / 笔刷数据 | 3 ~ 4 | 地形 → splat / 草 → density map / 草 → 风 | 3 ~ 4 | **重**（地形是大型分块数据） |
| 6 水体 | WaterPlaneComponent / FFT 状态 / 涟漪 RT | 2 ~ 3 | 水 → SkyAtmosphere、水 → 反射相机 | 1 ~ 2 | 中 |
| 7 场景管理 | 八叉树 / HZB / 渲染线程化双缓冲 | 0 | 但**整套 Scene 索引结构**会被深度耦合 | 1 | **重**（八叉树+多线程往里压一层 OO 索引） |
| 8 后处理 | RT 链、Tonemap、Bloom、AA | 0 ~ 1 | 主要是 RT 资源链，不是 Object 关系 | 1 | 轻 |
| 9 寻路 | NavMesh、AgentComponent、PathRequestQueue | 2 ~ 3 | agent ↔ navmesh、agent ↔ target Object | 2 | 中 |

合计（80% 完成度时，假设跑到 Phase 7 末尾）：

- **新增组件类型 ≈ 14 ~ 22 种**（vs 现在 0 种实战组件）；
- **新增跨实体引用关系 ≈ 12 ~ 18 条**（vs 现在 4~5 条）；
- **新增编辑器面板 ≈ 14 ~ 18 个**（vs 现在约 5 个）；
- **新增系统级耦合 ≈ 八叉树 / HZB / 多线程 / NavMesh** —— 每一个都和 `Scene::draw` / `Object::globalMatrix` 深度纠缠。

每一行都是"未来 ECS 化必须重做一次"的代价。

## 3. 成本曲线的两条路径

### 3.1 失控路径（默认惰性走法）

每个 phase 的功能都按 OO 直觉塞进去：

- 在 `Object` / `Mesh` / `Scene` 上加成员；
- 各 phase 维护自己的 `LightManager` / `ShadowManager` / `TerrainManager` 全局静态；
- Skin / Animation 继续用 `Object*` / `ObjectID`；
- 编辑器面板各自直接调 `m_selectObject->light()->setColor(...)` 这种深路径；
- `Transform` 在 `PhysicsScene` 里又 cache 一份；阴影里又 cache 一份；剔除里又 cache 一份。

这种路径下做 ECS 化时要：

1. 重写所有 phase 添加的 Manager → System；
2. 把所有"分散的全局状态"重新聚到 World；
3. 解决 N 份 Transform 副本之间的同步债；
4. 重做所有编辑器面板的取数路径；
5. 序列化全部重写（每个 phase 各自的 yaml schema 没有统一规范）。

成本爆炸的来源**不是组件多**，而是**这些组件互相引用、各自全局化、各自起 manager**。这就是为什么在大型 OO 引擎上做 ECS 重构的故事都很惨（Unity DOTS 的"convert authoring → runtime"工具就是为了对付这种局面而生）。

> 观察：Unity 的 DOTS 推了 8 年还在让 GameObject 与 Entity 混跑；UE5 的 Mass 也是只承担"群体 AI 子集"。两家都没有把已有的 OO 重构成 ECS，反而是**新功能优先用 ECS**。这就是失控路径的经验性证据。

### 3.2 纪律路径（按 04 推荐路线建设）

每个 phase 都遵守同一套护栏（详见 §4），每个新功能默认以**组件**的形式落地，且数据所有权清晰。这种路径下做 ECS 化时：

1. **组件已经是组件**，只需要把存储从"散布在 Object 内"换成"World 内的 SOA"；
2. **Entity = ObjectID 已经统一**，所有 `Object*` 引用退化为 ID 引用是机械替换；
3. **Transform 是单源权威**，没有副本同步问题；
4. **编辑器走 `getComponent<T>` 的统一入口**，迁移时只换实现不换接口；
5. **序列化走统一的 component schema**，迁移是逐组件 schema 升级。

代价仍然存在（组件多了，每个都得迁），但每个组件的迁移成本是**线性的、独立的、可分阶段的**。

## 4. 守住数量级的 5 条护栏

如果你只想保留"未来低成本切 ECS"的可能性，下面 5 条是性价比最高的护栏（都不是 ECS 改造，是 OO 内部纪律）：

### 护栏 1：新功能默认是组件

每个 phase 引入新行为时，第一选择是 **`class XxxComponent : public Component`**，挂到 `Object::m_components`，而不是给 `Object` 加成员、不是加全局 `XxxManager` 单例。

例外只允许给 **"热点"**：固定槽位 `m_fixComponents[FIX_COMPONENT_TYPE_XXX]`。物理设计文档已经预留了这个口子。

### 护栏 2：Transform 是唯一权威

无论 Phase 1 光照、Phase 2 阴影、Phase 3 物理、Phase 5 地形怎么扩展，**绝不允许 Transform 数据出现第二份副本**：

- 物理 body 的 transform 由 `Object::m_transform` 推送，物理结果回填走 setter（已经在物理设计文档里写过）；
- 阴影 cascade 的视图矩阵不缓存到光源对象上，每帧重算或显式 dirty；
- 八叉树存的是 `Object*` 或 `ObjectID`，不存 transform 拷贝。

这条护栏直接消除"未来 ECS 化时必须解决 N 份 Transform 同步"的最大头债务。

### 护栏 3：身份用 Entity，不用裸指针

新代码引用其他对象时优先用 `int entity = obj->id()` + `Object::objectByID(id)`（或未来的 `world->get(entity)`），而不是缓存 `Object*`。

例外：树父子链可以直接用 `Object*`（因为 Object 自己 own children，生命周期一致）。

最容易踩坑的是：
- 阴影 / 光照 / 物理回调里挂 `Object*` 监听 → 应该挂 ID；
- AI agent 的"目标对象"用 `Object*` → 应该用 ID；
- 序列化里写 `Object*` 的指针值或裸偏移 → 应该写 ID。

### 护栏 4：不要起 Manager 单例

每出现一个 `XxxManager` 全局单例 / 静态对象，就是未来 ECS 化的一道墙。Phase 1~9 里有强烈"我也起一个 Manager 吧"诱惑的地方：

- `LightManager`（光源列表）—— 实际上是 `for each Object with LightingComponent` 的批处理；
- `ShadowManager`（阴影分配）—— 实际上是 `for each LightingComponent with castShadow` 的批处理；
- `PhysicsScene` —— 这个**确实**需要单例（Jolt 的限制），但它的"跨界面"必须是 Entity，不能是 Object*；
- `NavMeshManager` / `TerrainStreamingManager` 等 —— 都应该是 World 内的"system 函数"，不是新加的全局类。

这条护栏与 Phase 7 的"渲染线程化双缓冲"高度相关：双缓冲数据本身可以走 World 的"this frame / next frame"两份组件存储，将来很自然过渡到 ECS 的 frame data。

### 护栏 5：序列化走统一 component schema

每个组件类型必须实现 `save(yaml::node&) / load(const yaml::node&)`，而不是把字段散落到 `Object::save()` 一坨里。

```yaml
- entity: 42
  components:
    transform: { move: [...], rotate: [...], scale: [...] }
    lighting:  { type: directional, color: [...], intensity: 1.0 }
    physics:   { type: rigidbody, mass: 1.0, ... }
    navmesh:   { agent_radius: 0.5 }
```

未来 ECS 化时，序列化层是 **0 改动**的（schema 已经按组件分块）。这是最便宜也最被低估的护栏。

## 5. 反向思考：哪些 phase 实际上**降低**了未来改造难度？

不是所有 phase 都增加 ECS 成本，有些 phase 反而**减少**：

- **Phase 0** 的 typed opaque handle / dirty flag / 引用计数 Texture：把"void* 资源句柄"改成强类型 ID，本身就是 ECS 友好的设计。Phase 0 完成之后，未来 ECS 不再需要重新搞资源句柄系统。
- **Phase 0** 的 Transform dirty flag：消除"每次访问都乘父链"的 OO 内禀依赖，把层级遍历变成一次 pass，是后期"ECS 中实现 transform system"的现成蓝图。
- **Phase 7** 的八叉树 + 视锥剔除：如果按"`scl::octree<Entity>` 而不是 `scl::octree<Object*>`"实现，剔除系统天然适配未来 ECS。
- **Phase 7** 的渲染线程化双缓冲：双缓冲帧数据本身就是 ECS / job system 的母题。

换句话说，Phase 0 / Phase 7 的功能是**架构投资**，质量足够高时反而**让未来 ECS 化更便宜**。这与 Phase 1~6 的"业务功能"是不同性质的代价。

## 6. 如果真的要在某个时间点做，最佳时机是？

按上面的拆分，最佳时机由"已偿还的债务"决定：

| 时机 | 优势 | 劣势 | 评级 |
|------|------|------|------|
| 现在（Phase 0 之前） | 无历史债 | task2 全推迟，光照都没看到 | 不推荐 |
| Phase 0 之后 | 基础设施扎深，opaque handle / dirty flag 都准备好 | 仍然没有"必须 ECS"的 demo | 不推荐（必要性不足） |
| Phase 3 之后 | 物理已经组件化，是检验"组件挂 Object"模式上限的好节点；可以这时候评估"物理是否要迁到 World"； | 仍然没有大量同质实体需求 | 可选评估 |
| Phase 5 期间 | **草地实例 / 雪沙脚印 / RVT 是天然 ECS 候选**；这个时候启动模式 B（World 旁路）有具体使用场景 | 范围必须严格收敛在"批量植被" | **推荐评估点 1** |
| Phase 7 之后 | 八叉树 + 多线程已就位，是"ECS 系统调度"的天然继承者 | 此时 task2 已基本完成 80%，是不是还要做 ECS 取决于后续路线 | **推荐评估点 2** |

注意 Phase 5 的草地 / Phase 6 的水体粒子 / 未来粒子系统都是模式 B（World 旁路）的天然客户，**让它们直接用 World 而不是 Object**，就是在现实场景中练手 ECS，不需要"专项重构"。

## 7. 操作建议（落到具体动作）

在 `task2.md` 的 phase 推进里嵌入下面 6 条，无需新增专项：

1. **Phase 0 期间**：把 04 推荐的"Object 组件 API 收紧 + Entity=ObjectID 统一"做掉（顺便修 `releaseObjectIDMap` 未置 NULL 的 critical bug）—— 1~2 周顺手做，不立专项。
2. **每个新 phase 开工前**：检查本 phase 引入的新行为是否能落到组件，不能就显式记一笔"OO 直挂"理由。
3. **每 6~8 周**：抽半天对照本文 §4 的 5 条护栏过一遍代码，遇到失守的地方建 issue。
4. **Phase 5 草地落地时**：让 `GrassInstance` 直接进 `World`，不进 `Scene` —— 这就是模式 B 的第一次实战。
5. **Phase 7 完成后**：重新评估本文档结论，决定是否启动"PhysicsComponent 迁移到 World"或更大动作。
6. **永远不**：在没有具体性能 demo 或具体业务需求的情况下，启动"全量 ECS 重构"。

## 8. 一句话总结

> **延后会让数量级的差距出现，但只在"放任失控"的前提下；只要在 Phase 0~3 立好 5 条护栏（组件优先、Transform 单源、ID 引用、不起 Manager、统一 schema），延后到 Phase 5 / Phase 7 之后再做 ECS，成本只是 2~3×，不是 10×。所以问题不是"什么时候做"，而是"路上要不要带着 ECS 友好的纪律走"。**
