# 03 — 改造必要性评估

> 上级：[README.md](./README.md)
> 关心问题：现在做 ECS 改造**值不值得**，未来什么时候才**值得**。

## 1. ECS 通常解决什么问题

把"是否值得"放回 ECS 的本质收益上看：

| 收益 | 触发条件 | cat 现状是否触发 |
|------|----------|------------------|
| 大量同质实体的 cache-friendly 批量更新 | 单帧需要遍历更新数千~几万个同类组件 | 否（典型场景 < 数百 Object） |
| 任意切片组合的可组合性（避免继承爆炸） | 需要 N 种正交行为 × M 种实体类型的笛卡尔积 | 否（行为种类很少） |
| 多线程 system 调度（Job） | 需要把 transform / animation / physics-sync 拆成可并行 system | 否（主循环单线程足够） |
| 网络复制 / 状态同步的天然组件粒度 dirty | 多人联机 / 服务器权威 | 否（无网络需求） |
| Data-driven 流水线（编辑器外配置） | 大量配表驱动的实体类型 | 否（手工 Sponza / DamagedHelmet） |
| 流式加载 / 大世界 | 跨 chunk 实体迁移 | 否（task2 中"场景管理"是 Phase 7 的 3 周事项，不是 ECS 必须） |

**全部为否**。这意味着当前 cat 没有一项"非 ECS 不可"的需求。

## 2. cat 当前的真实瓶颈在哪里

来自代码审查（`doc/代码审查-逻辑.md` / `代码审查-性能.md` / `代码审查-崩溃安全.md`）的一手证据：

| 类别 | 数量 | 是否与 ECS / OO 选型相关 |
|------|------|--------------------------|
| Critical 必崩 | 13 | 完全无关（NULL 解引用、自递归、union 误用、`delete (void*)` 等） |
| Warning 行为 / 性能 | 30+ | 主要是 dirty flag 缺失、矩阵反算、视锥剔除缺失、48MB uniform buffer 治理 —— 都可在 OO 上一次性解决 |
| 跨平台编译 | 多项 | 与架构选型无关（include 大小写、`-Wreorder`） |

`task2.md` Phase 0 / Phase 1 / Phase 2 的工作内容里没有任何一项是"OO 做不到必须 ECS"。Phase 0 提到的全部是：

- Critical 修复
- include 大小写、clang-format / clang-tidy
- typed opaque handle、引用计数 Texture / Shader
- Transform dirty flag、视锥剔除、ImGui FrameStats、Uniform buffer 拆分

这套基础设施做完，cat 的渲染瓶颈基本就压住了，**完全不依赖 ECS**。

## 3. 业界对照

| 引擎 | 主线选择 | 备注 |
|------|----------|------|
| Unreal Engine | OO（UObject）+ Component（UActorComponent） | Mass / Iris / Niagara 等 ECS 是**子系统级旁路**，不是主干 |
| Unity | OO（GameObject）+ Component | DOTS / ECS 多年 preview，2023 之后才稳定，且与 GameObject 长期共存 |
| Godot | OO + Scene / Node | 没有官方 ECS |
| Bevy / flecs / EnTT 用户 | 全 ECS | 多用于 ECS-first 的玩法引擎、大规模模拟 |
| O3DE | Component-Entity（接近 ECS） | 仍保留场景层级 |

cat 的定位（`doc/架构总览.md`）是"面向学习和实验目的的轻量级 3D 引擎"。学习路线对照的是 RTR4 / GPU Pro / UE，**这些参考资料的代码模型都是 OO**。把 cat 切到 ECS 反而会让"对照 UE 学习"变难。

## 4. 物理引擎接入文档的实际决策

`doc/物理引擎接入设计与实施计划.md` §4.6 已经明确写过：

> cat 当前 `World` / `Component` 是雏形（`world.h`、`component.h`），未与场景图耦合。物理组件**不**走 `World`，而是用 `Object::m_components`，理由：
> - 形状/碰撞与变换是强耦合的，`Object` 已经持有 `Transform`，复用它最直接。
> - `World` 现在没有遍历器、没有 system，强行接入会先要把 ECS 写起来，超出 P1 范围。
> - P3+ 当 ECS 完整后，可以再做一次"PhysicsComponent 迁移到 `World`"重构。

这是一个已经做出的项目级决策：**物理走 OO + Object 组件，不走 ECS。** 这条决策与本评估的结论一致，互相佐证。

## 5. 现在就做 ECS 的代价

把 `02-改造难度评估.md` 的 12~19 周代价摆进 `task2.md` 的时间轴：

```
原 task2 Phase 0 (4w) → Phase 1 光照 (8w) → Phase 2 阴影 (6w) → Phase 3 物理 (5w) → ...
插入 ECS 改造 (12~19w):
  情况 A：放在 Phase 0 之后  —— 光照推迟 3~5 个月，且 ECS 完成时还没渲染收益
  情况 B：放在 Phase 7（场景管理）—— 此时已有 OO 实现的光照 / 阴影 / 物理 / 地形，迁移代价更大（要把已有功能也迁过去）
  情况 C：与 Phase 1~3 并行  —— 单人不可行
```

任何一种排法都是显著负向 ROI。

## 6. 未来什么时候必要性会变高

按优先级从高到低，下列任一信号出现可以重新评估：

1. **大量同质实体进入主线**：
   - 粒子系统（千~百万粒子）
   - 植被实例渲染（十万棵草 / 树）
   - 群体 AI / Boid（数千 agent）
   - 弹幕 / 子弹 / 投射物

2. **多线程化的渲染前置**：
   - Visibility / culling system 想做并行化
   - Animation / Skin 想做 Job 化
   - Physics-sync 想做并行 readback

3. **大世界 / 流式加载**：
   - 大于 16 平方公里、需要 chunk-level 加载
   - 实体可能在不同 chunk 之间迁移

4. **网络化**：
   - 需要"组件粒度 dirty"做差量复制

只要这四类信号都没出现，OO + Object 组件容器就是更优解。

## 7. 必要性结论

| 维度 | 评级 |
|------|------|
| 现阶段必要性 | **低**（无任何 ECS-only 需求） |
| 未来 1 年内必要性 | **低~中**（除非引入粒子 / 植被） |
| 未来 2 年以上 | **依赖项目走向**（粒子 / 大世界 / Job 化必然推高必要性） |
| 现在硬上的预期收益 | **负 ROI**（推迟主线 3~5 个月 + 引入回归风险） |
| 推荐当下动作 | **不立专项；保持 `World` 雏形不萎缩；先把 task2 Phase 0 / 1 走完** |
