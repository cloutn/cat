# cat 引擎 — 物理引擎接入设计与实施计划

> 上级：[架构总览](./架构总览.md)
> 关联：[子系统-cat](./子系统-cat.md)、[子系统-testCat](./子系统-testCat.md)、[子系统-第三方依赖](./子系统-第三方依赖.md)

本文给出 cat 引擎接入物理引擎的完整设计与分阶段实施计划。范围覆盖：候选物理引擎评估与选型、新模块 `catphysics` 的边界与抽象、形状/世界/查询/事件四类核心 API、与现有 `Object/Scene/Camera/Pick Pass/Gizmo` 的集成点、分里程碑的落地步骤、风险与跨平台/许可证注意点。

## 0. TL;DR

- 用户给的仓库 [NVIDIA-Omniverse/PhysX](https://github.com/NVIDIA-Omniverse/PhysX) 是正确的：这是 PhysX 5（NVIDIA 开源 BSD-3）的官方仓库，是接入 PhysX 应使用的入口。但**它不是唯一也不一定是最优选**，详见 §2 评估。
- 推荐 **首选 Jolt Physics**（许可证宽松、构建简单、主流引擎在用、移动端友好），**备选 PhysX 5**（功能最全、生态熟悉、可演进到 GPU/CUDA）。这两个都建议通过 `IPhysics` 抽象层接入，便于以后替换。
- 不建议在第一阶段自研：第一阶段需求（相交、拾取、射线）虽然技术上可以自研，但要做到稳健、性能合理、可演进（动力学、约束、CCD）成本远超直接接入成熟库。
- 第一阶段把"物理"分成两层来落地：
  - **碰撞查询层**（Phase 1 真正需要的）：BVH/AABB-Tree + 每个 `Object` 一个 collider proxy，提供 overlap/raycast/sweep。
  - **动力学层**（Phase 2+）：刚体、约束、触发器、连续碰撞、角色控制，逐步开启。
- 物理拾取（射线）和现有 GPU Pick Pass 不互斥，建议**共存**：射线做 Hover / 持续追踪 / 离屏查询；GPU Pick 仍可作为像素精确兜底。

## 1. 背景与目标

### 1.1 现状

cat 是 Vulkan 主线、glTF 资源、ImGui+ImGuizmo 编辑器的轻量引擎（见架构总览）。当前与"物理"擦边的能力只有两个：

1. `cat::Box`（`catbase/cat/box.h`）：AABB，仅提供 `intersect` / `combine` / `encapsulate`，没有空间索引、没有射线相交。
2. `Pick Pass`（见 `Client::_clickSelectObject`，`testCat/client.cpp` 第 258 行起）：用 GPU 颜色编码渲染一遍场景，回读单像素反查 `Primitive*`。功能正确但代价 = 一次额外渲染 + readback；不适合 Hover、不适合非屏幕查询、不能在没有相机/视口的上下文里使用。

没有任何刚体、碰撞体、物理世界、约束、CCD、触发器抽象，也没有 BVH 这类空间索引。

### 1.2 接入目标（按优先级）

| # | 目标 | 阶段 | 说明 |
|---|------|------|------|
| 1 | 构建物理世界，判定两个 `Object` 是否相交 | P1 | overlap test，AABB / OBB / 形状级别可分两步 |
| 2 | 鼠标 click / hover 选中物体 | P1 | 屏幕 (x,y) → 世界射线 → 物体 |
| 3 | 任意射线与场景求交 | P1 | RaycastClosest / RaycastAll，返回 hit 信息 |
| 4 | 形状扫掠（sweep）求交 | P2 | 比如胶囊体扫一段位移检测着地、墙体 |
| 5 | 触发器（Trigger / Overlap 事件） | P2 | onEnter/onStay/onExit 回调 |
| 6 | 刚体动力学（重力、速度、力、冲量） | P3 | `RigidDynamic` + integrator |
| 7 | 静态 / 动态 / 运动学三类 actor | P3 | 对应 UE 的 Static / Simulated / Kinematic |
| 8 | 约束（铰链、固定、距离、6DOF） | P4 | 编辑器侧的可视化与序列化 |
| 9 | 角色控制器（CCT） | P4 | 胶囊 + 滑动响应 |
| 10 | CCD（连续碰撞检测） | P4 | 高速物体穿透对策 |
| 11 | 异步并行模拟、子步长、确定性 | P5 | UE 物理子步与 RHI/Render 解耦的等价物 |
| 12 | 可视化调试（线框、碰撞体颜色） | 全程 | 接入 ImGui + 现有 simple shape 路径 |

> 目标 1~3 是"必须"。目标 4~12 是"以后该做"，本设计同样给出能演进到那里的接口与模块边界，避免一期写死。

### 1.3 与 UE 的常用需求映射（参考 F:\ue56）

UE 4.26 的 PhysicsCore + Engine 中，引擎常用物理需求大体可归纳为以下几类（`UWorld::SweepXxxByChannel`、`LineTrace*`、`UPrimitiveComponent::OverlapComponent`、`AActor::ComponentOverlapMulti`、`UPhysicsAsset`、`FBodyInstance` 等）：

- **场景查询（Scene Query）**：LineTrace / Sweep / Overlap，支持 single / multi、closest / any / all，支持按 channel、object type、actor 过滤。这是最高频用法，编辑器拾取、AI 视野、武器命中、移动判定都靠它。
- **碰撞响应（Collision Response）**：`ECollisionChannel × ECollisionResponse` 矩阵决定 Block / Overlap / Ignore。`FCollisionFilterData` 编码到 PhysX/Chaos 的 filter shader。
- **触发器与碰撞事件**：`OnComponentBeginOverlap` / `EndOverlap` / `Hit`。
- **物理资产（Physics Asset）**：骨骼模型的多球/胶囊/凸包，以及 Constraint 设置；用于 ragdoll 与角色物理。
- **CCT 角色控制器**：UE 的 `UCharacterMovementComponent` 内部实际是 sweep + slide，不直接用 PhysX CCT，但形状求交是骨架。
- **车辆 / 布料 / 流体**：UE 用 PhysX Vehicle / Cloth / FleX 或 Chaos 对应模块。优先级低，cat 引擎短期不考虑。
- **可视化与调试**：`ShowCollision`、`p.Chaos.DebugDraw.Enabled`、PIE 中的物理调试。

落到 cat 上，**P1 只覆盖"场景查询"中的 raycast + overlap，P2 增加 sweep + 触发器，P3 加入刚体动力学，P4 加约束 + CCT**。这与 UE 的"先有 query、再有 dynamics、最后有 constraints/character"演进路径一致。

## 2. 物理引擎候选评估

下表针对 cat 的目标场景（PC + 桌面级编辑器，Vulkan，C++17，自有 `scl` 数学，Windows 主线）做横向比较。

| 候选 | 许可证 | 体量 | 主要优点 | 主要缺点 | 适配 cat 难度 |
|------|--------|------|----------|----------|---------------|
| **PhysX 5**（NVIDIA-Omniverse/PhysX） | BSD-3 | 大（数百 KLOC） | 工业级；UE/Unity 长期使用过；功能最全（CCT、Vehicle、Cloth、CUDA）；用户熟悉度高；GPU 加速可演进 | 构建系统重（自带 PxBuildSDK）；头文件要 PxFoundation/PxPhysics/PxScene/PxShape/PxRigidActor 整套接入；移动端工具链支持没有以前好；CMake 集成不如 Jolt 干净 | 中高 |
| **Jolt Physics**（jrouwe/JoltPhysics） | MIT | 中（约 80 KLOC） | 现代 C++17/20；CMake 一键集成；多线程任务系统优秀；Horizon Forbidden West / Godot 4 实绩；移动端友好；性能与 PhysX 同档 | 生态比 PhysX 小；Vehicle/Cloth 等周边模块仍在演进；中文资料少 | 低 |
| **Bullet 3**（bulletphysics/bullet3） | zlib | 中 | 开源时间最久、教程多；Blender 在用 | 单线程瓶颈；API 偏旧；性能与稳定性逊于 PhysX/Jolt | 中 |
| **ReactPhysics3D / Newton / ODE** | zlib / 各异 | 小~中 | 轻量；学习成本低 | 维护活跃度参差；功能不全；性能差距明显 | 低~中 |
| **自研** | 自有 | 取决于范围 | 完全契合 `scl` / `IRender` 风格；零外部依赖；可学习 | P1 即需 BVH + GJK/EPA + 射线相交；要稳到能 ship 至少 3~6 人月；动力学/CCD/约束之后是无底洞 | 高 |
| **Chaos Physics**（UE 内置） | 与 UE 绑定 | 大 | UE 用得到 | 与 UE 模块深度耦合，剥离极困难；许可证不友好独立项目 | 不可行 |

### 2.1 用户找到的仓库是否正确

> 确认：`https://github.com/NVIDIA-Omniverse/PhysX` 就是 **PhysX 5 SDK** 的官方开源仓库（NVIDIA 在 2022 年用 BSD-3 开源后，由 Omniverse 团队维护）。如果决定走 PhysX 路线，应该 clone 这个仓库的 release 分支（例如 `release/105.x`），用其自带的 `PxBuildSDK_*` 脚本生成 lib，再让 cat 链接。

不过它**不是唯一选项**，也不是接入门槛最低的选项。下面先看 UE 的取向，再给本项目的推荐。

### 2.2 UE 4.26 / 5.x 的实际选型

- **UE 4.26**：默认仍是 PhysX 3.4（Engine/Source/ThirdParty/PhysX3）。Chaos 在 4.26 是预览状态，需要专门切换。
- **UE 5.x**：默认 Chaos，PhysX 已下线。

也就是说"UE 用 PhysX"是 4.x 时代的事实，到 5 已经迁移完。这意味着如果"和 UE 对齐"是核心诉求，PhysX 是合适的；如果"长期演进"才是诉求，PhysX 5（独立 SDK，不是 UE 内的 PhysX 3）反而是个全新的接入面，和 UE 4.26 内部 PhysX 3 调用约定差异不小。

### 2.3 推荐结论

- **首选 Jolt**：cat 体量小、移动端是潜在目标、CMake 子项目接入与 cat 现状（每个第三方都是 `add_subdirectory`）天然契合；MIT 许可证最干净；P1~P4 全部需求都覆盖。
- **次选 PhysX 5**：如果团队对 PhysX API 已经非常熟悉、或者明确要走 GPU/CUDA 物理路线（cat 已经是 Vulkan，未来对 GPU 物理友好），那直接用 PhysX 5 也合理。
- **不要自研**：第一阶段就要 BVH + 形状相交 + raycast，自研的开发与维护成本远高于接入。`scl` 数学和 `Box` 可保留，作为物理引擎与 cat 之间的"形状描述层"。
- **不要用 Bullet**：除非许可证或团队历史强约束，否则现代项目没有理由选 Bullet。

> 下文设计的接口层（`IPhysics` / `PhysicsScene` / `PhysicsBody` / `PhysicsShape` / `PhysicsQuery`）**不依赖于具体引擎**。第一版用 Jolt 实现，后续若切到 PhysX 5 只换实现层，业务侧无感。

## 2.4 许可证、构建、跨平台备注

| 库 | License | 商用 | 备注 |
|----|---------|------|------|
| PhysX 5 | BSD-3-Clause | 可 | 必须保留版权声明；不能用 NVIDIA 名义背书 |
| Jolt | MIT | 可 | 只需保留 LICENSE 文件 |
| Bullet | zlib | 可 | 最宽松 |

构建：

- Jolt：`add_subdirectory(free/JoltPhysics/Jolt)`，目标名 `Jolt`，`testCat` 直接 `target_link_libraries`。需要 `-DCPP_RTTI_ENABLED=OFF -DCPP_EXCEPTIONS_ENABLED=OFF` 与 cat 现状一致。
- PhysX 5：`PxBuildSDK_<plat>.bat` 产出 lib，再在 `free/PhysX/lib64/` 列入；和现在 `shaderc_combined.lib` 的接入风格相同。

跨平台：

- Windows（主线）：两者都开箱可用。
- Android：Jolt 已知有人 ship；PhysX 5 NDK 工具链需要自己折腾。优先 Jolt。
- iOS：同上。
- Apple Silicon：Jolt 原生支持；PhysX 5 已修复但不官方 release。

## 3. 模块设计

### 3.1 新增模块 `catphysics`

按 cat 现有的"接口在 `cat`、实现在独立模块"的拆分风格（参考 `cat::IRender` 与 `catvulkan::VulkanRender`），新增：

```
cat/catphysics/                    模块根
├── cat/
│   ├── physicsDef.h               枚举（BodyType / ShapeType / QueryFlags）
│   ├── physicsShape.h             形状描述（值类型，CPU 侧）
│   ├── physicsBody.h              actor 句柄包装（值类型 ID + 实现指针）
│   ├── physicsScene.h             world / scene 抽象（接口）
│   ├── physicsQuery.h             query 输入 / 输出结构
│   └── IPhysics.h                 ★ 物理后端抽象接口
├── jolt/
│   ├── joltPhysics.h/.cpp         IPhysics 的 Jolt 实现
│   ├── joltScene.h/.cpp           PhysicsScene 的 Jolt 实现
│   └── joltShape.h/.cpp           shape 创建 / 缓存
└── CMakeLists.txt
```

依赖方向：

```
testCat ──▶ cat ──▶ catphysics(接口) ──▶ catphysics/jolt ──▶ free/JoltPhysics
                       └─ 依赖 catbase（Box / Transform / Camera）
                       └─ 依赖 scl（容器 / 数学）
```

`cat` 模块只 include `catphysics/cat/IPhysics.h` 等纯接口，不接触 Jolt 头。这与"`cat` 不接触 Vulkan 头、只用 `IRender*`"的现有约束一致。

### 3.2 接口分层（必看）

```
IPhysics                  顶层服务（生命周期、世界创建）
 └─ PhysicsScene          一个物理世界（一个 cat::Scene 对应 0..1 个 PhysicsScene）
      ├─ PhysicsBody*     物理物体（actor），由 ID 索引
      │   └─ PhysicsShape 形状（box / sphere / capsule / convex / mesh）
      ├─ raycast(...)
      ├─ overlap(...)
      ├─ sweep(...)       P2
      ├─ simulate(dt)     P3
      └─ debugDraw(IRender*) 可选
```

四类对象都是**值类型 ID + 接口指针**，与 cat 现有的"`Object` 用 `int m_id`、可由 `objectByID` 反查"风格一致。

### 3.3 关键类型设计

#### 3.3.1 `PhysicsShape`（CPU 侧形状描述）

```cpp
namespace cat {

enum PHYSICS_SHAPE_TYPE
{
    PHYSICS_SHAPE_TYPE_INVALID = -1,

    PHYSICS_SHAPE_TYPE_BOX,
    PHYSICS_SHAPE_TYPE_SPHERE,
    PHYSICS_SHAPE_TYPE_CAPSULE,
    PHYSICS_SHAPE_TYPE_CONVEX_HULL,
    PHYSICS_SHAPE_TYPE_TRIANGLE_MESH,
    PHYSICS_SHAPE_TYPE_PLANE,

    PHYSICS_SHAPE_TYPE_COUNT,
};

struct PhysicsShape
{
    PHYSICS_SHAPE_TYPE      type;
    union
    {
        struct { scl::vector3   halfExtent;                                 } box;
        struct { float          radius;                                     } sphere;
        struct { float          radius;     float       halfHeight;         } capsule;
        struct { const scl::vector3* points; int        pointCount;         } convex;
        struct { const float*   vtx; int    vn; const uint32* idx; int in;  } mesh;
        struct { scl::vector3   normal;     float       d;                  } plane;
    };
    scl::vector3            localOffset;        // 形状相对 body 的偏移
    scl::quaternion         localRotation;
};

} // namespace cat
```

理由：

- 用 union/POD 描述，避免每形状一个 class 带来的 vtable 膨胀；与 `KeyFrame`（`AnimationChannel.h`）的 union 风格一致。
- `points` / `mesh` 指针只在 `IPhysics::createBody` 时被消费（拷贝到后端的 cooking buffer），不持有；与 `Primitive::setIndices` / `setVertices` 的"调时即用"风格一致。
- `localOffset / localRotation` 让一个 body 可以挂多个 shape（compound shape，UE 的 BodyInstance 也是这种结构）。

#### 3.3.2 `PhysicsBody`

```cpp
enum PHYSICS_BODY_TYPE
{
    PHYSICS_BODY_TYPE_STATIC,       // 不动，参与查询与碰撞
    PHYSICS_BODY_TYPE_KINEMATIC,    // 由 GameThread 直接 setTransform，参与查询与碰撞，不受力
    PHYSICS_BODY_TYPE_DYNAMIC,      // 受力、重力、约束

    PHYSICS_BODY_TYPE_COUNT,
};

struct PhysicsBodyDesc
{
    PHYSICS_BODY_TYPE           type;
    scl::vector3                position;
    scl::quaternion             rotation;
    scl::varray<PhysicsShape>   shapes;
    int                         ownerObjectID;      // 反查 cat::Object
    uint32                      filterGroup;
    uint32                      filterMask;
    bool                        isTrigger;
    float                       mass;               // 仅 PHYSICS_BODY_TYPE_DYNAMIC 用
};

class PhysicsBody
{
public:
    int                     id              () const;
    int                     ownerObjectID   () const;    // → cat::Object*
    PHYSICS_BODY_TYPE       type            () const;
    void                    setTransform    (const scl::vector3& pos, const scl::quaternion& rot);
    void                    setLinearVelocity(const scl::vector3& v);    // P3
    // ... 其他 P3 之后才暴露
};
```

`ownerObjectID` 是关键字段：所有 query 返回 hit body 之后，业务侧用它一次 `Object::objectByID()` 即可拿到 `cat::Object*`，与现有 `Env::registerPickPrimitive` 拿 `Primitive*` 的风格对应。

#### 3.3.3 查询输入/输出

```cpp
struct Ray
{
    scl::vector3    origin;
    scl::vector3    dir;        // 单位向量
    float           maxDist;    // 0 = 无限远
};

struct RaycastHit
{
    int             bodyID;
    int             ownerObjectID;
    scl::vector3    position;
    scl::vector3    normal;
    float           distance;
    int             shapeIndex;
};

struct OverlapHit
{
    int             bodyID;
    int             ownerObjectID;
};

enum QUERY_HIT_MODE
{
    QUERY_HIT_MODE_CLOSEST,
    QUERY_HIT_MODE_ANY,
    QUERY_HIT_MODE_ALL,
};

struct QueryFilter
{
    uint32          mask;
    int             ignoreBodyID;
    int             ignoreOwnerID;
    bool            includeStatic;
    bool            includeDynamic;
    bool            includeKinematic;
};
```

> 上面所有 `struct` 都需要在配套的 `.cpp` 里给出 ctor，按 cat 风格在 init list 中显式赋默认值（`mask = 0xFFFFFFFFu`、`ignoreBodyID = -1`、三个 `include* = true` 等），不在结构体里写 C++11 默认成员初始化。

#### 3.3.4 `PhysicsScene`

```cpp
class PhysicsScene
{
public:
    virtual ~PhysicsScene() {}

    // ---- 生命周期 ----
    virtual int             createBody          (const PhysicsBodyDesc& desc) = 0;
    virtual void            destroyBody         (const int bodyID) = 0;
    virtual PhysicsBody*    body                (const int bodyID) = 0;

    // ---- 同步（GameThread 修改 cat::Object 后调用一次） ----
    virtual void            syncBodyTransform   (const int bodyID, const scl::vector3& pos, const scl::quaternion& rot) = 0;

    // ---- 查询（P1 必须） ----
    virtual bool            raycast             (const Ray& ray, RaycastHit& outHit, const QueryFilter& filter) = 0;
    virtual int             raycastAll          (const Ray& ray, RaycastHit* outHits, const int capacity, const QueryFilter& filter) = 0;
    virtual int             overlap             (const PhysicsShape& shape, const scl::vector3& pos, const scl::quaternion& rot, OverlapHit* outHits, const int capacity, const QueryFilter& filter) = 0;
    virtual bool            overlapPair         (const int bodyA, const int bodyB) = 0;

    // ---- 模拟（P3 才用，P1 可空实现） ----
    virtual void            simulate            (const float dt) = 0;
    virtual void            fetchResults        () = 0;

    // ---- 调试可视化 ----
    virtual void            debugDraw           (IRender* render) = 0;
};
```

### 3.4 与 `cat::Object` 的绑定

不在 `Object` 里硬塞物理字段，而是新增一个 `PhysicsComponent`，挂到 `Object::m_components`：

```cpp
class PhysicsComponent : public Component
{
public:
    PhysicsComponent();

    int                         m_bodyID;       // PhysicsScene 中的 ID，-1 表示未注册
    PHYSICS_BODY_TYPE           m_type;
    scl::varray<PhysicsShape>   m_shapes;       // CPU 侧描述，便于序列化
};
```

理由：

- 不是所有 `Object` 都需要物理（编辑器 Grid、Light、Skybox 都不需要），用组件挂载是正交设计。
- 形状描述 `m_shapes` 留在 CPU 侧，是因为序列化（`Object::save`）、热重载、形状重构都需要 CPU 数据。Jolt 的 `BodyInterface` 句柄只是后端缓存。
- 与现有 `m_fixComponents`（`object.h` 第 104 行）的固定槽位机制兼容，可考虑增加 `FIX_COMPONENT_TYPE_PHYSICS` 槽，提高热路径访问速度。

绑定流程：

```
1. glTF 加载完 / 编辑器手动添加 → Object::addComponent<PhysicsComponent>(comp)
2. comp.m_shapes 由（自动 from boundingBox）或（用户在编辑器面板里编辑）填充
3. Client 在场景加载完成后遍历 Scene，对每个有 PhysicsComponent 的 Object：
       desc = build_desc_from_component(obj, comp)
       comp.m_bodyID = scene->createBody(desc)
4. 每帧 GameThread：if obj.transform changed → scene->syncBodyTransform(comp.m_bodyID, ...)
```

形状从 `Object` 自动推导的兜底策略（用户没显式配置时）：

- 取 `Object::boundingBox()`（已存在）→ 转 `PhysicsShape::Box`，`halfExtent = box.size() * 0.5f`，`localOffset = box.center() - object.position()`。
- 这能保证"任何 glTF 节点开机即可被 raycast/overlap 拾到"，是 P1 拾取替换 GPU Pick Pass 的最低代价。

### 3.5 形状级别与精度策略

借鉴 UE 的两层模型（Simple Collision vs Complex Collision）：

| 用途 | 推荐形状 | 备注 |
|------|----------|------|
| 鼠标拾取（粗） | Body 的 AABB | 最快 |
| 鼠标拾取（精） | Box / Sphere / Capsule / ConvexHull | 多数足够 |
| 像素级拾取 | TriangleMesh（来自 `Primitive::vertexPositions()`） | 慢，编辑器场景才开 |
| 玩法相交（动态） | Capsule + Box 组合 | UE 角色路线一致 |
| 静态环境 | TriangleMesh / Heightfield | Terrain 可直接喂 mesh |

cat 已经能拿到顶点（`Primitive::vertexPositions()` 走 GPU readback），所以**复杂三角网格碰撞理论上可在 P1 的 editor 工具里离线 cook**。但默认运行时只用 AABB / OBB，避免 readback 带来的卡顿。

### 3.6 过滤、Layer、Group

模仿 UE 的"channel × response"矩阵，但 cat 一期只做最小子集：32 位 group / mask（与 PhysX 和 Jolt 都对齐）。

```cpp
namespace cat {

enum PHYSICS_LAYER
{
    PHYSICS_LAYER_NONE          = 0,
    PHYSICS_LAYER_DEFAULT       = 1u << 0,
    PHYSICS_LAYER_SELECTABLE    = 1u << 1,      // 编辑器拾取专用
    PHYSICS_LAYER_CAMERA        = 1u << 2,      // 相机碰撞，P4
    PHYSICS_LAYER_TRIGGER       = 1u << 3,

    PHYSICS_LAYER_ALL           = 0xFFFFFFFFu,
};

} // namespace cat
```

编辑器拾取的 Query 只用 `mask = PHYSICS_LAYER_SELECTABLE`，把 Grid / Skybox / Light 这种"视觉对象"自动排除。

## 4. 与现有系统的整合

### 4.1 鼠标拾取（替换 / 共存 GPU Pick Pass）

现状：`Client::_clickSelectObject(x, y)`（`testCat/client.cpp:258`）走 GPU Pick Pass。

新流程（P1）：

```cpp
void Client::_clickSelectObject(int x, int y)
{
    Ray         ray     = _screenToWorldRay(x, y);     // 见 §4.2
    RaycastHit  hit;
    QueryFilter filter;
    filter.mask = PHYSICS_LAYER_SELECTABLE;

    if (m_physicsScene->raycast(ray, hit, filter))
    {
        m_selectObject = Object::objectByID(hit.ownerObjectID);
        m_gui.setForceOpenSceneTree(true);
    }
}
```

替代方案的取舍：

| 方案 | 延迟 | 内存 | 精度 | Hover 支持 |
|------|------|------|------|------------|
| GPU Pick Pass（现状） | 一帧 + readback | RT + 表 | 像素级 | 难（每帧一次太贵） |
| Physics Raycast（新） | 同步 / μs 级 | BVH | 形状级 | 容易 |

**建议保留 GPU Pick Pass 作为"精确拾取兜底"**，新增 Physics Raycast 作为默认路径与 Hover 路径。两者通过 `Config::usePhysicsPick` 开关切换。

### 4.2 屏幕坐标 → 世界射线

cat 的 `Camera`（`catbase/cat/camera.h`）已经有 `viewMatrix / projectionMatrix / matrix`，但**没有** unproject。需要在 `catbase/cat/camera.h` 增加：

```cpp
Ray Camera::screenToWorldRay(const int x, const int y, const int screenW, const int screenH) const;
```

实现：

```
ndc.x = 2 * x / W - 1
ndc.y = 1 - 2 * y / H        // 注意 Y 翻转
near_world = inverse(VP) * (ndc, 0, 1)   // Vulkan: 0；OpenGL: -1
far_world  = inverse(VP) * (ndc, 1, 1)
ray.origin = near_world / w
ray.dir    = normalize(far_world / w - ray.origin)
```

注意 `Config::reverseZ` 会改变 NDC z 取值，要把 `Camera::zRange()` 与 reverseZ 一起进入计算。

### 4.3 Hover 高亮

新增 `Client::_updateHoverObject()`，每帧从鼠标位置发一根射线（`mask=Selectable`），命中物体时通知 `MainGUI` 在场景树高亮、并在 3D 视口画一层描边。这是 GPU Pick Pass 做不到的能力。

### 4.4 Gizmo 拖动期间

ImGuizmo 拖动时不能让物理 raycast 命中"被拖动物体自己"，否则 sweep 出错。`Client::_processGizmo()` 期间把选中物体临时 `disable`（在 PhysicsScene 中给一个 ignore mask 或 `setEnable(false)`），松开鼠标再恢复；与 UE 的"拖动期 actor 改 kinematic"思路一致。

### 4.5 与 Animation / Skin 的关系

P1 不处理。骨骼动画驱动的网格目前只更新 `jointMatrices`，不会改变 `Object::transform`，所以 body 本身位置稳定。P3 之后如果要让 ragdoll / 骨骼物理参与模拟，再扩展 `PhysicsComponent` 让每个 joint 一个 body，与 UE 的 PhysicsAsset 模型一致。

### 4.6 与 ECS（`World`）的关系

cat 当前 `World` / `Component` 是雏形（`world.h`、`component.h`），未与场景图耦合。物理组件**不**走 `World`，而是用 `Object::m_components`，理由：

- 形状/碰撞与变换是强耦合的，`Object` 已经持有 `Transform`，复用它最直接。
- `World` 现在没有遍历器、没有 system，强行接入会先要把 ECS 写起来，超出 P1 范围。
- P3+ 当 ECS 完整后，可以再做一次"PhysicsComponent 迁移到 `World`"重构。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Jolt 与 cat 的数学库不一致（行/列主序、Y/Z up） | raycast 命中不正确 | 在 `joltShape.cpp` / `joltScene.cpp` 写一层 vector/quaternion 转换函数，单元测试覆盖三个轴 |
| `Object::globalMatrix` 含 scale，物理形状 cooking 时未应用 scale | 命中位置偏 | cook 时把 scale 烘进 `halfExtent / radius`，运行期不再传 scale |
| Pick mask 与 GPU Pick 行为不一致 | 用户报"以前能选这个，现在选不到了" | 默认 `Selectable` 自动覆盖所有有 mesh 的 `Object`；保留 GPU Pick fallback |
| Triangle mesh cooking 卡顿 | 大场景启动慢 | M1/M2 不开 mesh，仅 AABB；M3 加缓存到磁盘（`.cache/`）|
| 移动端工具链 | NDK 构建 PhysX 5 复杂 | 优先 Jolt；PhysX 一期只做 Win64 |
| 物理与渲染线程冲突（P3+） | 数据竞争 | 借鉴 UE：物理在自己的 task；GameThread 只在 simulate 之外读写 actor；double-buffer transform |
| EOF 空行规则 | 修改 `object.h / camera.h` 时增删空行 | 严格保留原 EOF 状态（见个人规则） |

## 7. 自研可行性评估（补充）

如果未来确实想替换为自研物理，最小可行集合：

| 模块 | 需要实现 | 难度 | 估时（个人） |
|------|----------|------|--------------|
| AABB 树 / BVH | `AABBTree`，insert/remove/refit | 中 | 1 周 |
| 形状求交（GJK + EPA） | 凸形对凸形距离 + 穿透深度 | 高 | 2~3 周 |
| Ray 对各形状 | Box/Sphere/Capsule/Mesh | 中 | 1 周 |
| 三角网格 BVH | mesh-level BVH + 射线相交 | 中 | 1 周 |
| 触发器与回调 | event 队列 | 低 | 2 天 |
| 约束求解器 | 顺序冲量 / PGS | 高 | 3~4 周 |
| CCD | sweep + TOI | 高 | 2 周 |
| 多线程化 | island、分组 | 高 | 2~3 周 |

合计**仅查询层就 4~5 周**，进入 dynamics 后还要再 2~3 个月。Jolt / PhysX 接入到 P1 完整可用是 1 周以内。结论：**P1~P3 强烈不自研**，P4+ 若有特殊需求（确定性回放、定制求解器），可以局部自研单一模块替换接口实现。
